# PR02 · 资源、任务与关闭

生产宿主直接消费六包真实Cordis cohort。诊断在bootstrap创建根Context后、插件apply之前就绪；资源和任务服务由显式boot或ctx.plugin安装。行为验收见[生产测试](<tests/pr02.test.mjs>)，补丁及来源沿用PR01。

## 一、接口

资源归调用者的真实Fiber持有；服务自身寿命与调用者的资源寿命分别记录。两个消费者共享服务时，卸载一方会清理其租约，另一方继续使用原资源。

```ts
import { createHost, OwnedResources, TaskSupervisor } from '@society0/host';
const host = await createHost({boot: []});
await host.ctx.plugin(OwnedResources, {closeTimeoutMs: 30_000});
await host.ctx.plugin(TaskSupervisor, {concurrency: 4, maxPending: 1024, maxBytes: 64 * 1024 * 1024});
```

[resources](<packages/host/src/resources/index.ts>)提供`open(factory,label?)`、`use(label,closer)`和`closeReport()`。factory返回`{value,close}`或该对象的Promise，open返回可await的`{value,close()}`租约；use直接登记异步closer。报告区分opening/open/closing/failed，保留失败资源的编号、标签、owner及错误；成功关闭通过closed累计计数记录。

[tasks](<packages/host/src/tasks/index.ts>)提供`run(label,task,{signal?,bytes?})`、`drain(reason)`、`requestClose(reason)`、`snapshot()`和`bind()`。并发、排队上限与字节预算按调用者Fiber分配；每个owner直接复用p-limit7.3.3并启用rejectOnClear。active/pending计数和字节描述尚未物理结束的真实记录。bytes由知道原生缓冲大小的适配器提交，表示本次任务保留的预算；排队取消在真正移出队列前仍占相应记录与预算。

run返回真实Promise并附带`settled: Promise<void>`：取消signal使等待方尽早得到拒绝；settled在执行体实际结束、或派发前从队列清除后完成。取消后的原生错误继续进入诊断。调用方的执行许可应在settled时归还；入队校验可能同步抛错，该路径尚未创建物理任务。

```ts
const task = ctx.tasks.run('native-query', signal => worker.query(signal), {signal: callerSignal, bytes: 4096});
void task.settled.then(() => permit.release());
const result = await task;
```

任务内部使用requestClose请求其owner关闭；该方法返回void并脱离当前任务的AsyncLocalStorage执行上下文启动真实Fiber.dispose。drain用于等待物理结束，同一任务直接等待自己的drain会得到TASK_SELF_JOIN。

[diagnostics](<packages/host/src/diagnostics/index.ts>)提供`report(record,owner?)`和`snapshot()`。诊断保留稳定owner身份、真实Fiber树与effect标签，最近1000条错误及省略数量；closeFailures单独累计，历史截断保持关闭判断。资源cleanup错误会令Host保持halted，已被调用者处理的普通task失败保留证据并允许资源完成关闭。

## 二、顺序

原生required binding与结构child决定provider退役时的清理顺序。对外方法继续采用真实Cordis追踪代理；物理执行器需要在setup明确登记自身owner。

数据库等provider可在退役期间被旧consumer的cleanup调用。setup时调用`const executor=ctx.tasks.bind()`得到闭包绑定的TaskScope；其run/drain/requestClose持有原provider owner。旧binding清理查询在native dependent-drain阶段仍可运行；进入provider自身task-drain后，新任务被拒绝。普通ctx.tasks.run保持调用方所有权及激活状态检查。

```ts
const executor = ctx.tasks.bind();
const lease = await ctx.resources.open(async () => ({
  value: await openWorker(),
  async close() {
    await executor.drain('database closing');
    await closeWorker();
  },
}), 'database-worker');
ctx.provide('database', {
  query: (sql: string) => executor.run('query', signal => lease.value.query(sql, signal)),
});
```

资源与任务位于同一个Fiber时，closer按上例显式等待自身执行器。Cordis中同一owner的独立顶层effect维持并发。另一种结构是资源provider与required任务consumer分别拥有资源及任务，由原生依赖屏障负责先排空consumer。

[Host.close](<packages/host/src/bootstrap.ts>)返回status/drained/diagnostics/resources/tasks。失败抛HostCloseError，report保留实际残留。close的timeoutMs覆盖resources.closeTimeoutMs；已安装resources的默认关闭期限为30000ms。超时返回halted、drained=false，底层原生close继续执行，后续close仍join原transition；真实结束后drained=true，halted判断保留。原生disposer持续等待实际cleanup完成，依赖资源在等待期间继续保留。

## 三、验收

[生产行为测试](<tests/pr02.test.mjs>)采用真实文件句柄、node:sqlite同步查询所在worker以及127.0.0.1临时端口HTTP流。测试使用可控barrier制造未完成窗口，完整结果与失败先行日志保留在[PR02证据目录](<../../evidence/pr02/>)。

| 门 | 实际消费者与证据 |
|---|---|
| T01 | 两个调用者分别拥有文件句柄；关闭一方后另一方stat仍可用，owner UID准确 |
| T02 | SQLite原生调用进入worker后取消awaiter；真实执行结束前activeCount和activeBytes保留 |
| T03 | HTTP响应结束后再关闭server；结构child在provider退役后通过预绑定scope完成真实SQLite查询 |
| T04 | resource cleanup故障保留残留与halted；异步acquire被关闭时等待factory并精确close一次；原生补丁回归覆盖setup/observer/重复disposer |
| T05 | 任务内部requestClose返回并排空，pending拒绝，另一owner继续执行；原生回归覆盖PENDING依赖环 |
| T06 | 原生任务取消后立即申请后继任务；pending字节与上限可见，后继未越过物理额度，事件循环继续响应 |

[仓外类型消费者](<tests/pr02-types.ts>)检查公开augmentation及Promise/lease类型。[打包验收脚本](<scripts/acceptance.py>)在全新仓外目录安装tarball，运行这些生产消费者、真实CLI及原生Cordis回归。CLI cleanup故障必须非零退出，stderr包含残留标签。

PR02负责物理任务与资源清理。世界写许可、generation失效和完整点发布由后续执行fence/SQLite服务消费这里的真实settled信号，并通过自己的消费者验收。


## 阶段验证与共享发布

PR02生产资源/任务/诊断共15项行为门已通过；独立用户链审查覆盖真实资源失败、超时、取消后容量、旧SQL binding清理和owner隔离，未发现P1，见[独立报告](../../evidence/pr02-independent-e2e/REPORT.md)。重复完成后的lease.close始终返回Promise；resources.use保留原生disposer身份，返回void或Promise。

本阶段可复用的仓外候选为[consumer-03结果](../../evidence/pr02/consumer-03/result.json)：10个真实tarball独立安装，strict类型消费者与93项组合门通过。[组合日志](../../evidence/pr02/051-all-package-acceptance.log)覆盖PR01/原生回归、PR02、CLI、出口映射、PR03配置、execution-fence以及PR04真实SQLite；[工件门](../../evidence/pr02/052-all-artifacts.log)验证全部出口、许可、声明、lock与两条有序补丁。[仓外sidecar门](../../evidence/pr02/055-published-sidecars.log)通过真实ModuleResolver检查并导入host13/core4个声明入口。后续活跃PR使用新的构建边界。

现有CLI支持显式boot的通用命令调用；input按所选命令的schema提供：

```text
society0 --boot <boot.json> --command <name> [--input <json>]
```

boot需装配commands及相应命令提供者。成功结果在命令实际完成且Host关闭后输出JSON。SIGTERM/SIGINT通过invocation.signal交给命令，CLI等待命令完成再关闭Host；中断命令退出非零。原有无句柄未完成清理保持Node exit 13，资源超时保持Host halted。

[共享构建](scripts/build.py)支持可重复的--package，保留未选择产物；默认构建全部登记包。原生SQLite直接装配已构建.node和随包库。公开入口目录决定生产TypeScript范围，同目录worker随入口编译，其余活跃开发目录在登记就绪前保持隔离。

[Sidecar生成器](scripts/sidecars.mjs)收集模块真实导出的Config/metadata/api，确认Config与实际插件同一引用；Schema使用自身toJSON。来源记录实际git HEAD、有序补丁文件名和公开hostAbi。dirty工作树以及运行时transform/自定义校验限制显式写入静态检查结果。

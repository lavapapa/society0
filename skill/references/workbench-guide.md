# Society0 静态实验工作台

实验配置已有初稿，或者已有保存结果，且研究者选择创建工作台后，先编写该实验的数据转换脚本，再用 `../scripts/render_workbench.py` 把转换后的数据写入 `../assets/workbench-template.html`，产出一个静态 HTML 文件。工作台可在首次试运行之前展示配置，随后把各配置版本的试运行结果纳入同一页面。页面中的配置修改只是暂存提议；研究者复制变更并发送给 agent，经核对后才会修改实验文件。数据或配置版本有更新时，需要重新执行转换并生成文件。页面不连接运行中的实验，也不负责启动、暂停或调整实验进程。

页面共享紧凑的版本、试运行和 tick 控制条。“实验检查”保留三栏：左侧列出 Agent、环境与制度等视角；中间展示配置字段、FoV 机制及专题标签；右侧展示待发送变更、Agent 会话和其他有依据的记录。有社交资料时增加“关系网络”和“帖子浏览”，社交实验默认进入关系网络。选择“配置视图”即可回到版本初始配置。可按研究需要修改模板的样式和组件。

配置版本与试运行选择放在品牌旁，使用随所选文本伸缩、有最大宽度的下拉控件；主要页面入口组成明确的标签组。切换主体与时点时，保留仍然适用的当前标签，便于连续比较。折叠与展开使用带可访问名称和提示的图标。复制变更的完整请求应内含“核对原值、创建新配置版本、更新工作台、暂时不运行”，研究者粘贴发送即可；自动复制失败时提供同一份完整文本。

## 按研究任务调整模板

把附带 HTML 当作可修改的起点。先判断研究者要核对什么，再决定数据转换、页面组织和呈现方式。agent 可以修改模板的布局、图标、组件和交互，查询并内联适合的可视化库，也可以制作新的专题 HTML。保留可读的定制源码与生成入口，让后续配置和结果更新能够重复生成。

1. 列出当前资料支持的阅读任务：配置检查、关系结构、帖子及回复、主体会话、结果比较。根据已有资料选择入口；社交网络实验把关系网络和帖子浏览放在主要位置。
2. 按资料的重要性分配空间。用户列表、ID、时间、来源和筛选使用紧凑样式；帖子正文、机制资料、关键结果和会话原文获得主要阅读空间。来源等次要信息可折叠，长正文提供展开阅读，长列表采用虚拟滚动或分页。用图标辅助识别，图标按钮提供名称和悬停提示。
3. 先调整现有页面与机制模块中的标签和组件。若研究任务需要独立的比较、时间线、地域图或其他专题页，先告知研究者新增页面的用途及额外时间、token 消耗，再确认是否制作。例如：“这批资料适合增加跨版本对照页，能并排检查〔具体指标〕；制作和验收会额外花一些时间与 token。需要一起做吗？”已有授权覆盖该扩展时直接执行。
4. 使用单个 HTML 内的页面切换，或按明确阅读目的拆成多个自包含 HTML。各页保留版本、运行、时点的定位信息和相互入口。交付时告诉研究者哪一页适合先看，以及哪些资料尚未整理。

模板的组件预设供选择与改造。数据的实际价值决定是否更换组件、扩大正文区域或增加页面；为每个实验保留必要的来源与时点含义。

## 生成流程

为每项实验保留一个可重复执行的数据转换脚本，例如 `analysis/build_workbench.py`。脚本读取各版本实际使用的配置和各版本下已有的试运行产物，按下面的数据格式生成 `workbench-data.json`，再调用 skill 中的 HTML 生成脚本。尚无试运行时，`runs` 写空数组。资料与呈现逻辑由实验自己的转换脚本决定；通用生成脚本只负责检查基本结构并把 JSON 嵌入单文件模板。

配置检查页面可以在引擎安装和模型准备期间先交付。HTML 生成脚本仅依赖 Python 标准库；从独立配置文件或实验源码中的配置定义提取数据即可，避免为了展示草稿而导入会初始化引擎的入口。页面说明中分别标明“配置草稿”“初始化检查结果”和“已有试运行”，研究者可以先确认设定，再进入技术检查。

```text
各版本的实际配置 + 各版本下已保存的试运行结果（可以为空）
  → 实验目录中的 build_workbench.py
  → workbench-data.json
  → skill/scripts/render_workbench.py
  → workbench.html
```

生成 HTML 的脚本这样调用：

```bash
python skill/scripts/render_workbench.py \
  --data experiments/study/analysis/workbench-data.json \
  --output experiments/study/workbench.html
```

上例从 Society0 仓库根目录执行；skill 安装在其他目录时，用该 skill 的实际路径替换脚本路径。

可以用 `--template` 指向按本实验修改过的 HTML 模板。若添加了专用组件，把改动留在该模板副本中，重新生成时便不会丢失。将生成 HTML 的步骤写入 `build_workbench.py`，让更新工作台只需执行一个实验脚本。交付给研究者的是生成后的 HTML；浏览版本、试运行、tick 和主体仅会切换该文件内已保存的数据。页面暂存的配置修改在刷新或关闭后可能丢失，务必复制并发给 agent；复制动作本身也不会保存实验文件。

更新通用模板时，保留实验数据转换脚本与原始记录，确认数据格式仍适用后采用新版模板并重新生成页面。有专用组件时在其可读源码中核对和整合改动；压缩 HTML 的逐字符比较可能耗时很长，选择结构、具体样式规则或组件源码来定位差异。遇到长时间比较或取消回复后仍在执行的命令，核对并停止该次后台任务，再继续生成；更新模板沿用已保存资料即可。

## 版本目录与变更回传

强烈建议在单个研究项目内按配置版本组织文件，让试运行归属于生成它的版本：

```text
experiments/study/
  versions/
    v001/
      experiment.py
      runs/
        pilot-001/
          runner-status.json
          runner.json
          current.sqlite
          steps/
    v002/
      experiment.py
      runs/
  analysis/
    build_workbench.py
    workbench-data.json
  workbench.html
```

版本目录名称可以按项目习惯调整。若配置分散在 Python 代码、JSON、环境定义和模型参数中，转换脚本应提取该版本的实际配置快照，写入 `version.config`，并在 `configSource` 标明真实来源；不要只复制一份与实际运行脱节的展示文件。每个版本的 `entities`、`runs` 都写在该版本内，未运行版本也可以独立检查。目录规范由 skill 强烈建议，不要求 Society0 运行时强制执行；已有项目可保留自身结构，只要转换脚本准确表达版本与运行归属。

收到 `society0_config_change_request` 时，agent 先核对 `baseVersionId`、`configSource` 和每条 `before` 与当前源文件是否一致，再按 `op`（`add`、`remove`、`replace`）判断 `after` 是否符合实验约束。若源文件与页面快照已有差异，先向研究者说明冲突；若变更成立，创建新的版本目录并修改其中的实验定义，保留旧版本及其运行结果，重新提取配置、生成工作台。JSON 路径指向工作台提取出的配置树；当源配置在 Python 中时，agent 负责把路径映射回真实代码。除非研究者另行要求，不自动启动试运行。

复制出的请求例如 `{"type":"society0_config_change_request","baseVersionId":"v001","configSource":"versions/v001/experiment.py","changes":[{"op":"replace","path":"/agents/0/persona","before":"谨慎读者","after":"热心读者"}]}`。研究者可以在粘贴后附上原因或补充要求；agent 仍需以实验文件为准核对，不把浏览器里的草稿当作已生效配置。

同名 Python 配置模块按各自绝对文件路径加载，例如用 `importlib.util.spec_from_file_location(f"config_{version_id}", path)`；先确认导入配置不会启动实验。逐版本核对实际字段，避免模块缓存把后续版本全部读成第一版。初始化检查的零 tick 记录标为“配置检查”，失败记录标明失败及其原因，完成的试运行才提供相应结果。根据 `runner-status.json` 的 `status`、`complete_step` 与实际阶段结果判断，目录存在本身不足以判断成功。

## 首次交付给研究者

顶部左侧写研究项目名称，中间放页面切换，右侧放版本、试运行和 tick 选择；研究问题可通过项目名提示查看，主内容尽量占满可用横纵空间。实验检查的左栏先放研究者最关心的主体，也可放“实验整体”“环境”“制度实体”等视角；各主体标明类型。配置版本尚无运行时，中间默认展示所选视角对应的配置字段及解释，研究者可改动字段，必要时展开当前视角的 JSON 编辑器增删字段；右栏显示待发送变更。已有保存结果时，为 LLM Agent 准备默认的“可接触的信息”视图，按机制说明它在当前 tick 能接触哪类资料；右侧优先展示该 Agent 在当前 tick 的真实会话。没有记录时显示空状态，缺少依据的标签不添加。无论是否已有运行，顶部都要明确显示当前版本和试运行范围。

配置阶段也为每个 Agent 保留独立入口，用 `group` 标明所属实验条件；组级概览可额外添加。这样研究者能逐一检查 persona、属性和状态，并在试运行后沿用同一个主体入口查看会话。环境按其实际含义命名和归类，例如普通消息环境可以是 `overview`，政府等制度实体才使用相应类型。

向第一次打开页面的研究者，简短介绍三种阅读路径：先选配置版本，检查主体和环境设定；如想提议修改，编辑字段并复制顶部变更请求发给 agent；如有试运行，切换到该版本的试运行，沿 tick 查看机制、会话与变化。对复杂机制的解释，可补充几个“你可能还想看”的入口，指向相关主体、相邻 tick 或专题视图。页面中的说明应围绕研究问题，不使用界面实现术语代替解释。

在宿主应用内交付时，确认最后显示的是 HTML 页面，并让研究者知道如何从产物卡片重新打开。内嵌预览若未允许自动复制，模板会显示变更文本框；提示研究者选中文本、复制，再粘贴回同一会话即可。此时仍保留尚未发送的草稿，收到请求后再核对与创建版本。

## 转换的数据格式

转换脚本输出的 JSON 有 `study`、`versions` 两个顶层字段。HTML 生成脚本会替换模板中的 `society0-workbench-data` 数据块，并处理 JSON 中可能出现的 HTML 结束标签。版本 ID 在整个工作台内唯一，其余 ID 在同一版本、同一次运行等各自范围内保持唯一。`config` 是可序列化的完整配置树；`configPath` 是该观察对象在 `config` 内的 JSON 路径，省略时展示整个配置树。若路径穿过数组，给数组元素保留稳定的 `id`，以便研究者调整数组顺序后仍指向同一主体。环境参数、Agent 字段和实验条件都可放进同一配置树，转换脚本不要擅自遗漏需要研究者核对的字段。

```json
{
  "study": {"title": "研究项目名称", "question": "这项研究要解释什么？"},
  "versions": [
    {
      "id": "v001", "name": "初稿", "configSource": "versions/v001/experiment.py",
      "config": {"agents": [{"id": "agent-a", "persona": "..."}], "environment": {"type": "plain"}},
      "entities": [
        {"id": "agent-a", "name": "主体 A", "kind": "llm-agent", "group": "参与者", "configPath": "/agents/0"},
        {"id": "environment", "name": "环境", "kind": "overview", "group": "实验设定", "configPath": "/environment"}
      ],
      "runs": [
        {"id": "pilot-001", "name": "试运行 1", "ticks": [{"id": "1", "label": "Tick 1"}],
         "snapshots": [{"tickId": "1", "entityId": "agent-a", "mechanisms": [], "tabs": [], "sessions": [], "sideTabs": []}]}
      ]
    }
  ]
}
```

`kind` 可用 `llm-agent`、`rule-agent`、`institution`、`overview`，也可按研究需要扩展。每个 snapshot 归属于一个配置版本下的一次试运行，并对应一个 tick、一个观察对象。切换时只读取完全匹配的 snapshot，缺失的记录保持空白；不要把最终状态填到早期 tick，也不要跨版本或试运行复制数值。非 LLM 实体可以有中间专题标签和右侧事件标签；工作台不会替它生成 Agent 会话。

### 配置字段的解释与视角划分

转换时为每个可编辑字段提供 `version.configFields`，键为配置树的 JSON 路径，值包含中文 `label`、解释含义和单位的 `description`、说明调整后影响的 `effect`。数组位置可用 `*`，如 `/agents/*/persona`；具体路径优先。说明根据实验配置定义、提示词与调度代码填写，已知的取值范围和相互约束写进解释。尚未确认的含义标为待确认，并在交付前补齐。

```json
"configFields": {
  "/agents/*/persona": {
    "label": "人设说明",
    "description": "主体的背景与行为倾向，由本实验的人设提示词引用。",
    "effect": "修改会改变后续实验中的角色设定，建议创建新版本对照。"
  }
}
```

“实验整体”聚焦环境、全局参数和实验条件。为其设置对应的 `configPath`（例如 `/environment`），主体配置由左栏各主体入口呈现。若全局参数分布在多个分支，可增加有明确含义的检查视角或定制分区；保持原始配置路径与变更回传一致。逐项确认完整配置中的研究参数都有检查入口。

## 社交网络与帖子浏览

使用 social network 环境时，将关系网络和帖子浏览作为工作台的主要入口，与实验检查共享版本、试运行和 tick。转换脚本在 `version.social` 填入初始配置资料，在 `run.socialSnapshots` 填入逐时点的完整社交快照；每项的 `tickId` 与 `run.ticks` 精确匹配。当前时点缺失时显示空态。快照中的帖子正文、回复、点赞和关系状态均截止该时点，删除关注等变化由转换脚本处理。

每个社交快照使用以下字段；具体领域可增添字段和呈现方式：

```json
{
  "tickId": "1",
  "source": "本次运行的实际产物与完整步骤",
  "nodes": [
    {"id":"agent-a","label":"主体 A","kind":"agent","group":"参与者","entityId":"agent-a"},
    {"id":"post-1","label":"帖子 1","kind":"post"}
  ],
  "edges": [{"id":"edge-1","source":"agent-a","target":"post-1","type":"publish","tick":1}],
  "posts": [{"id":"post-1","author":"agent-a","title":"帖子 1","content":"原始正文","tick":1,"likes":[],"replies":[]}],
  "feeds": {"agent-a":["post-1"]}
}
```

节点与边的 ID 在当前网络中唯一；帖子 ID 与其网络节点 ID 相同，`entityId` 对应版本中的观察对象。关系的 `source`、`target` 为端点 ID，`type` 支持 `follow`、`publish`、`reply`、`share`、`like` 和实验自定义类型；具体出处可写入 `sourceRef`。社交主画布的节点 `x`、`y` 使用 Cytoscape 模型坐标，例如相邻节点相隔 140，省略时模板自动排列；这与下文机制卡片 `network` 组件的 0–1 坐标不同。帖子回复逐项使用 `{id, author, content, tick}`。`likes` 可为明确计数或已保存的点赞主体数组，缺失时页面显示未记录。

`feeds` 按主体 ID 给出当前时点保存的推荐范围帖子 ID，数组顺序即引擎写入的原推荐顺序。未整理该主体资料时省略对应键；已核实为空时填空数组。模板用这些 ID 筛选轮末帖子，页面标为“推荐顺序”，不提供时间或热度重排；互动数与正文分别给出“收到时 → 轮末”两列，说明左值是激活当时的注入内容、右值是轮末累计。ID 列表不足以还原激活当时的完整内容与顺序，实际注入通过实验检查中的会话查看。若新增“当时的信息流”视图，保存并展示对应 Thread 中的完整帖子快照、原推荐顺序与激活标识，勿从轮末帖子补回当时未知的互动。

通用结果导出器保留 Results 与 Thread；社交投影通过实验自己的转换脚本从领域记录补充。真实运行的交付需同时填入 `run.snapshots` 与 `run.socialSnapshots`，在页面点开至少一位主体的会话、动作回执和运行产物。`snapshots: []` 会使主体视角停留在配置检查。避免从零散动作结果推测完整网络。

帖子浏览沿用“用户 → 发布的／推荐顺序 → 正文与回复”的阅读路径，支持作者与内容搜索、排序、跳转关系网络和主体检查。用户行右侧显示当前快照的发帖数与点赞给出数；所有帖子都有点赞主体数组时，按主体 ID 计算其点过赞的帖子数，缺失数组时显示“—”。帖子收到的点赞总数另在帖子预览中呈现。帖子行紧凑排列作者、时点、互动数、标题与摘要，ID 放在详情的次要信息行，回复采用可折叠的附属区域。用户和帖子列表采用虚拟滚动，全文保留在详情及原始记录中。长回复树或大型网络可由 agent 按实际规模扩展分页、分层或其他组件。

默认交付一个包含多个页面的自包含 HTML，切换页面保留该文件中的配置草稿。也可分别生成不同默认入口的文件，例如 `--view network --output network.html`、`--view posts --output posts.html`、`--view inspect --output inspect.html`。这些文件各自包含完整数据和界面；不同文件中的草稿分别管理，更新时从同一转换结果重新生成。若按资料规模进一步拆分数据，保留共同的版本与运行标识、页面间链接及各页导出范围。

## FoV 机制与专题模块

`mechanisms` 中每项对应一种 FoV 机制。机制卡片的 `access` 取 `available`、`unavailable` 或 `unknown`，分别表示已确认当前可接触、已确认当前不可接触、尚无足够依据。填写 `description` 说明机制能提供哪类资料，`reason` 说明当前状态下的适用条件，`source` 写实验定义或状态记录的具体出处。只看到能力目录登记时，使用 `unknown`；只有确认主体、条件和 tick 的适用规则后，才使用 `available`。可接触状态与会话保存范围分别判断：原始输入未保存时，确定性的规则与当时状态仍可支持“当前可接触”；会话中的实际注入内容则标为缺失。

```json
{
  "id": "fov-example",
  "name": "机制名称",
  "access": "unknown",
  "description": "这个机制能提供哪类资料。",
  "reason": "当前主体与 tick 的适用条件尚待核实。",
  "source": "实验定义中的 FoV 注册与调用条件",
  "views": [
    {"id": "explain", "title": "机制说明", "type": "text",
     "paragraphs": ["机制提供资料的范围与限制。"]},
    {"id": "information", "title": "可接触资料", "type": "table",
     "columns": [{"key": "item", "label": "资料"}, {"key": "value", "label": "内容"}],
     "rows": []}
  ]
}
```

示例中的空 `rows` 由转换脚本填入该主体、该轮次可接触的资料，并注明来源；资料尚未取得时保留空状态及其原因。两种视图属于同一机制模块，避免再创建一个同名的顶层“可接触的信息”标签。

机制卡片同时呈现信息边界和边界内的资料。先根据主体、tick 和环境规则整理可接触范围，再为每种机制选择组件：消息流可用虚拟表格，关系范围可用网络，历史数值可用时间序列；说明和资料可以分别放在同一机制的 `views` 标签中。例如，主体有权查看十条消息，本轮实际注入三条，中间展示十条可接触消息及其范围依据，右侧会话保留实际注入的三条。未执行过的机制也可处于可接触状态，依据来自当时规则与保存状态；资料不足时标明未知。所有数值对应当前快照，避免把最终资料填入早期 tick。

会话中真正执行过的 FoV、注入的具体资料及 Agent 后续动作，依据真实交互记录在会话中呈现。研究者需要的其他内容放在 `tabs`；每个标签含 `id`、`title` 和 `modules`。模块含 `id`、`title`、可选 `description`、`source`、`wide` 与 `views`。右侧 `sideTabs` 采用同样的标签与模块结构；没有资料支持时直接省略。

每个 `view` 都有 `id`、`title`、`type`。预设呈现方式如下，agent 可按资料性质选择，也可以扩展：

| type | 主要字段 | 适用资料 |
| --- | --- | --- |
| `text` | `paragraphs: [字符串]` 或 `text` | 机制解释、定性记录 |
| `metric` | `items: [{label, value, unit?, note?}]` | 少量关键数值 |
| `timeseries` | `rows: [{x, y}]`、可选 `unit` | 随时间变化的单变量 |
| `candlestick` | `rows: [{x, open, high, low, close}]`、可选 `unit` | 具有开、高、低、收语义的序列 |
| `network` | `nodes: [{id, label, description?, x?, y?}]`、`edges: [{from, to, label?}]` | 主体或概念之间的关系；可选坐标取 0 到 1 |
| `table` | `columns: [{key, label}]`、`rows: [对象]` | 较长的事件、观察或结果清单 |
| `custom` | `renderer` 及自定义字段 | 预设组件无法恰当表达的资料 |

`table` 只渲染滚动视口附近的行；全部行仍在 HTML 的 JSON 中，文件大小和浏览器解析时间会随数据增长。K 线和时间序列默认展示最近 500 个时点并标明截取数量，可用 `maxPoints` 调整。数据量很大时，先按研究问题筛选或汇总，再决定是否开发分页、分层网络等更合适的组件。K 线需要真正的开、高、低、收含义；普通时间序列使用 `timeseries`。

自定义组件可以直接放在 HTML 的 `window.SOCIETY0_RENDERERS = {}` 代码块中。例如，把 `window.SOCIETY0_RENDERERS.matrix = (element, view, context) => { ... }` 定义为渲染函数，view 写 `{"type":"custom","renderer":"matrix"}`。函数接收容器、当前 version／run／tick／主体／snapshot；如需清理事件监听或图形资源，可返回清理函数。agent 可以查询和使用更适合的可视化方式，不受预设类型限制；需要离线单文件交付时，将依赖和样式一并放进 HTML。

## 会话与资料来源

`sessions` 中每次触发单独一项，`id` 唯一，`label` 建议包含交互名称和顺序。右栏会按这些真实会话给出选择菜单。会话的 `events` 依次填写输入、可见输出、动作或工具、观察结果、错误等记录；每项可用 `kind`、`title`、`text`、`data`、`time`、`source`。只展示原始记录中可核实的内容，工具名写真实名称，不补写隐藏推理。没有会话的 tick 留空数组。

可读摘要放在 `text`，完整原始 payload 放在 `data`，保留请求 ID、工具调用 ID、结束原因及来源的 Thread ID 和序号。若选择展示摘录，应明确标为摘录并指向完整记录。记忆策略中的 `recall_top_k` 标为“召回上限”，实际召回条数从本次输入计算。统计分别呈现初始投放、成功动作次数和新增领域事实数；重复点赞可能增加成功调用次数而不增加点赞关系，调用次数与形成的点赞关系分别写出。发帖记录的作者和帖子 ID 应按实际记录字段映射，并抽取一例核对。

跨轮内容分成三类呈现，不要合并：长期记忆（每轮提炼的短句，注入上限 `recall_top_k`）、当轮重新感知的帖子状态（平台在该轮激活时重读的正文与赞/评论数）、往轮会话原文（不进入本轮输入，只能作只读回溯）。FoV 中三者分开列出，避免把当轮重读的帖子当成记忆回放，或把记忆当成上一轮原文。

Next 引擎的结果与会话优先复用 `society0.kernel.workbench.export_payload`。它通过 Results 与 ThreadStore 读取完整步骤中的记录，并还原独立 payload 中的长内容。先从 `runner-status.json` 与 Results 确认已经完成的步骤，明确选择步骤号和主体，再导出：

```python
from pathlib import Path
from society0.kernel.workbench import RunSelection, export_payload

payload = export_payload(
    [RunSelection(Path(run_dir), version_id, tuple(complete_steps), tuple(actor_ids))],
    title=study_title,
    question=research_question,
)
```

上述变量由实验转换脚本提供。导出的 `tickId` 使用完整步骤号，显示标签保留业务时间；合并社交快照时沿用同一映射。主体的默认 `entityId` 为 `actor:` 加主体 ID；与配置页和社交节点合并时统一映射，避免出现有数据却无法选中的会话。导出器保留结果与 Thread 原文，实验转换脚本继续补充中文字段说明、配置入口、FoV 和社交投影。

测量表和规则动作记录放入 `tabs` 或 `sideTabs`；`sessions` 使用真实 Thread 事件，按线程区分触发并保留事件顺序和来源。根据事件内容调整输入、输出和工具记录的阅读样式。未保存的输入标明缺失；重建提示词标明重建。记忆提炼等附加调用按原始记录核对，资料范围如实注明。需要单独读取时，使用 `society0.kernel.observation.Observation` 的 `list_threads`、`thread_tail` 与 `read_thread_payload`，其参数以当前源码为准。

数据来源通过正式 kernel.workbench.export_payload 的 RunSelection 与 Observation/Results 读取：runner.json 给冻结合同，runner-status.json 给状态，阶段结果给指标、表和激活原文，Thread 给完整模型与工具会话，resource_usage/action_summary 给累计事实。巨记录沿 payload_ref 读取完整原文；原始业务值放在 value 内。共享信息目录不代表某主体已实际接触，须核对当时感知、权限与完整 Thread。业务 Moment.time 与完整步骤号分别保留。

## 交付前走完阅读流程

在研究者使用的浏览器中打开生成后的 HTML，按下面四条路径实际操作。可以使用宿主内置预览或经授权的本机预览；将观察到的问题修好后再交付。没有对应数据的路径，检查其空态并说明缺少什么资料。

| 路径 | 操作与验收 |
| --- | --- |
| 配置检查 | 选择无运行版本或“配置视图”；检查主体和环境字段；修改字段、暂存完整 JSON；核对差异和复制出的请求；切换页面和版本后核对草稿归属。实验源文件应保持原状，正式变更通过回传请求处理。 |
| 关系网络 | 选择保存时点，切换关注／帖子交互等图层；操作缩放、拖动、定位、重排与筛选；点击节点及关系查看两端、记录和来源；检查导出图片。使用实际图规模核对标签重叠和交互速度。 |
| 帖子浏览 | 选择用户，在“发布的”和“推荐范围”之间切换；提供真实曝光快照的定制页可命名为“信息流”。搜索、排序、滚动到列表末尾；展开帖子阅读，检查完整正文和回复；跳转网络及作者检查，再回到帖子。历史 tick 应保持当时的正文、回复和关系范围，实际推荐列表保留原顺序。 |
| 会话查看 | 从主体进入实验检查；对照 FoV 可接触资料与真实会话；选择同 tick 的多次触发，核对输入、输出、工具原文与来源；展开阅读长记录并收起，确认当前位置与选择仍可继续使用。 |

四条路径共用版本、试运行、tick 和主体定位。至少切换一次具有不同资料的运行，以及一次无运行版本，检查内容跟随正确范围。检查研究者常用窗口大小下的截断、面板滚动与键盘操作；重要正文应能展开，次要资料应可找到。原始配置或结果有变化时，重新执行转换脚本并刷新页面。

## 维护模板

实验定制模板保存在该实验目录。更新已安装 skill 时，从仓库 skill 同步到宿主安装目录，保留实验定制副本。要将实验中发现的通用改进纳入模板，应修改下述可维护源码并重新构建，避免直接回写实验 HTML。

可维护源码位于仓库的 `tools/workbench-template/`，使用 React、Vite 和原型的样式。需要修改预设组件或三栏交互时，在该目录运行 `npm ci`、`npm test`、`npm run build`，将 `dist/standalone/index.html` 复制到 `skill/assets/workbench-template.html`。普通实验更新数据时，修改或重跑实验的数据转换脚本，不必安装前端开发依赖。

# 从问题到可运行实验

这份 reference 处理最常见的起点：研究者有一句不太准确、比较随意的问题，比如“为什么大家都不信官方消息”“平台推荐是不是让人更极端”“这个政策会不会让人少说话”。目标不是马上写 profile，而是把它变成一个有比较、有主体、有环境、有记录、能试跑的实验。

整个流程有七步。每一步都写清：做什么、产出物、判断标准、常见坑。可以跳步，但跳过的部分要在设计记录里写明理由。

## 第 1 步：澄清问题

### 做什么

先把日常说法拆成四件事：

- **现象**：观察到的模式或困惑是什么？发生在什么场景？
- **研究问题**：要比较什么与什么？哪个是条件，哪个是结果？
- **分析单位**：判断落在个人、群体、帖子、组织、地区还是事件上？
- **结论范围**：这次实验最多能支持哪一类说法？

把“为什么”改成“在什么条件下，A 与 B 相比，结果 C 会怎样变化”。如果问题里同时有多个“为什么”，先选一个能在小实验里区分的。

### 产出物

一页以内的研究问题卡：

```text
现象：
研究问题：
比较对象：
结果变量：
分析单位：
时间范围：
这次不回答的问题：
```

### 判断标准

- 能指出至少一个反例或零结果的可能。
- 结果变量可以用记录中的字段、行动回执或测量题项表达。
- 能说清“如果结果是这样，说明什么；如果是那样，又说明什么”。
- 不把“验证某个宏观结论”直接写进主体提示。

### 常见坑

- 问题里塞了三个机制，却没有一个能被单独改变。
- 把“态度”“信任”“极化”当成一个数，没有写测量口径。
- 一开始就追求真实世界预测，忽略这次实验只是机制探索。
- 把研究者的结论写进主体可见材料，最后只能得到提示的回声。

## 第 2 步：找因素和路径

### 做什么

把问题拆成几条可能的机制路径。每条路径写清：起点、经过谁、在哪个环节改变、最后落到哪个可观测结果。常见路径有三类：

- **信息与可见性**：谁在什么时候看到什么，顺序、推荐、屏蔽、标注如何改变暴露。
- **制度与权限**：谁可以行动，谁被限制，违规会有什么后果，哪些行动会留下记录。
- **主体与时间**：哪些群体记得什么、在哪个阶段改变、一个 tick 代表什么。

然后区分：

- **要改变的因素**：这次实验的自变量。
- **要固定的因素**：主体构成、初始状态、种子、数据、时间长度、测量口径。
- **暂时不研究的因素**：写进限制，不要偷偷塞进人格或提示。

### 产出物

一张因素表：

```text
路径 | 因素 | 本次角色（改变/固定/不研究） | 作用环节 | 预期可观测差异
```

再加一张“替代解释”清单：如果看到差异，还可能是什么造成的？下一次比较如何区分？

### 判断标准

- 至少有一条路径能落到具体行动或环境状态，而不是只停在“认知”。
- 改变的因素只有一个主因素；如果是一个组合干预，明确写“这是组合条件”，不要声称分离了单个因素。
- 固定的因素能真的固定：种子、主体、初始数据、tick 数、测量题项。
- 替代解释能对应到下一次可执行的比较。

### 常见坑

- 同时改提示、主体和推荐权重，却声称比较了“推荐算法的影响”。
- 把本应固定的主体画像在不同条件里换成不同人。
- 只写“信息会传播”，没有写谁传给谁、在哪个时点、以什么形式出现。
- 把研究者关心的宏观量直接塞进每个主体的状态。

## 第 3 步：确定主体层和微观群体

### 做什么

先回答四个问题：

1. 谁能感知？
2. 谁能决定？
3. 谁能行动？
4. 谁承担后果？

只有同时需要“感知—判断—行动—承担后果”的实体才考虑做主体。机构、地点、产品、帖子、话题、资源、流程位置通常先做环境状态、记录或参数，不要默认都变成 agent。

然后确定微观群体：

- 哪些角色需要不同人格或初始状态？
- 哪些差异是研究条件，哪些只是噪声？
- 每个群体至少有几个主体？先少而清楚，再扩。
- 规则主体和 LLM 主体如何分工？

### 产出物

一张主体表：

```text
主体/群体 | 角色 | 可见信息 | 可行动作 | 可变状态 | 驱动（规则/LLM） | 数量
```

再加一张“非主体对象”表：

```text
对象 | 在环境中的角色 | 由谁维护 | 是否可见
```

### 判断标准

- 每个主体都有明确的可见范围和行动集合。
- 只作为记录、资源或流程的对象没有被强行赋予人格。
- 隐藏条件不在主体可见状态或人格文本里。
- 规则主体负责算术、权限、结算、调度；LLM 主体负责解释、语言、判断和策略。
- 第一版的主体数量能用手工检查逐个看完。

### 常见坑

- 把知识图谱的每个节点都做成主体。
- 用很长的人格文本替代环境状态和行动约束。
- 把“平台”“政府”“媒体”写成全知主体，给它们不该有的全局视野。
- 主体数量一上来就很大，导致无法判断是机制还是随机波动。

## 第 4 步：写 ODD

ODD 不是形式主义。它把“这个模型到底假设了什么”写成别人能检查的文字。可以按下面八块写，每块控制在几句话到一张表。

### 4.1 目的与范围

- 研究问题、比较对象、结果变量。
- 这次实验支持什么判断，不支持什么判断。
- 时间范围和 tick 的研究含义。

### 4.2 实体与状态

- 主体、群体、机构、资源、地点、帖子、事件。
- 每个实体的关键状态、取值范围、初始值来源。
- 哪些状态对主体可见，哪些只对研究者可见。

### 4.3 时间与调度

- 一个 tick 是什么：一次浏览、一轮对话、一天、一个政策阶段。
- 阶段顺序：先发生什么、后发生什么、哪些阶段可以并行。
- 干预在哪个 tick、哪个阶段进入。
- 运行何时停止：来源耗尽、达到 tick 上限、满足终止条件。

### 4.4 信息暴露

- 每个主体在每个时点能看到哪些来源。
- 信息的顺序、分页、截断和推荐如何影响可见内容。
- 主体看不到什么，为什么看不到。
- 感知材料是否保留原文和引用，展示是否截短。

### 4.5 行动与后果

- 行动名称、输入字段、可用条件。
- 行动成功后改变什么状态、写入什么记录。
- 规则拒绝和执行故障如何区分。
- 哪些行动是必需完成的，哪些只是可选。

### 4.6 交互与网络

- 谁与谁相连，边的来源和方向。
- 传播、推荐、配对、回复的规则。
- 关系变化是否进入状态，还是只作为记录。

### 4.7 随机性与不确定性

- 随机种子、随机地址和抽样规则。
- 哪些环节使用随机，哪些要求确定。
- LLM 的温度、请求预算、工具预算和截断处理。
- 重复运行如何组织。

### 4.8 观测与测量

- 每个 tick 记录什么：行动回执、状态、测量表、定性文本。
- 结果变量的计算口径。
- 缺失、失败、预算耗尽如何标记。
- 哪些量可以从记录重算，哪些是研究者判断。

### 产出物

一份 ODD 文档，附一张“条件—固定项—测量项”表。第一版不必长，但每个会影响解释的选择都要能指出来。

### 判断标准

- 读者能只靠 ODD 重建实验的主要结构。
- 每个结果变量都能追到记录或测量题项。
- 条件之间的差异只有一个主因素，且写清组合干预的边界。
- 随机性和 LLM 不确定性有明确处理方式。

### 常见坑

- ODD 只写主体人格，不写环境和暴露。
- tick 的含义在不同阶段变化，却没有说明。
- 测量题项和主体看到的材料混在一起。
- 没有写失败、截断和预算耗尽时结果如何解释。

## 第 5 步：选插件和 profile

### 做什么

先选最接近研究机制的公开 profile，再复制成自己的版本。不要从空文件拼一整套装配。

- **规则基线、状态更新、简单顺序实验**：从 `rule-sqlite` 开始，用 Core 的 `plain`、`actors`、`proposal-sequence`、`driver-rule`、`rule-passive` 或 `plain.update`。
- **信息流、帖子、关注、传播、推荐、社交感知**：从 `social-sqlite` 开始，用 Social 的仓库、初始化、拓扑、行动、感知、测量和推荐组件。
- **外部事件驱动**：从 `event-sqlite` 开始，用事件源和事件处理器。
- **需要 LLM 主体**：在 social profile 上保留 `driver-llm`、`model-pi`、`agent-runtimes`、`agent-runtime-pi`、`actor-tools`，按真实提供方设置模型和预算。

选择时逐项核对：

```text
研究机制 -> 需要的感知来源 -> 需要的行动 -> 需要的状态表 -> 需要的测量 -> 对应插件
```

插件字段以安装包里的 `Config`、`plugin.meta.json` 和 `--inspect` 的有效配置为准。`typescript/docs/plugin-config.md` 是字段目录，具体版本仍以实际安装包为准。

### 产出物

一份 profile 草稿和一张“机制—插件—配置项”对照表。对照表至少写出：

- 入口 id、插件名、作用域。
- 改了哪些配置，为什么。
- 哪些配置是实验条件，哪些只是运行参数。
- 哪些服务依赖由别的插件提供。

### 判断标准

- `society0 check --profile <profile.json> --json` 返回 `ok: true`。
- `missing` 为空；有 `warnings` 时逐条解释。
- 每个研究机制都能指到具体插件和配置，而不是“应该会自动发生”。
- 影响结果的配置变化使用新的 profile 和新的 run。

### 常见坑

- 直接改运行中的 run，而不是新建 profile。
- 把提供方地址、密钥或本机路径写进公开 profile。
- 看到 `ok: true` 就以为业务一定正确；`check` 只做静态装配。
- 为了跑通而删掉必需行动、完成条件或预算，导致结果不可解释。

## 第 6 步：补数据

### 做什么

按 ODD 列出需要的数据，再判断每类数据放在哪里：

- **主体画像**：角色、初始状态、可见属性。少量主体可以直接写在初始化配置里；规模大时用 world 文件或种子脚本。
- **刺激材料**：帖子、通知、新闻、对话开场、政策文本。保留原文和来源，展示时可以截短，但分析要能回到原文。
- **网络与关系**：显式边、随机拓扑、小世界、无标度、完全图或目标变异系数网络。写明生成规则和随机种子。
- **领域对象**：价格、库存、预算、配额、案件、课程、床位等。作为环境状态或公开表，不要写进人格。
- **测量表**：问卷题项、访谈提纲、评分规则、编码表。
- **外部事件**：时间、偏移、载荷、接收者。事件偏移必须递增，时间不能倒退。

数据缺失时，写“缺失”并说明对结论的影响。不要用语言模型生成的值冒充观测数据；如果生成的是情景材料，明确标注为情景。

### 产出物

一张数据清单：

```text
数据 | 来源 | 粒度 | 放哪里 | 谁可见 | 缺失时怎么处理
```

外加可复现的生成脚本或 world 文件。脚本要固定种子，输出目录不要覆盖已有版本。

### 判断标准

- 每个主体、每条边、每个刺激都能追到来源或生成规则。
- 主体可见的数据与研究者标签分开。
- 数据规模与主体数量、tick 数匹配，第一版能手工抽查。
- 重新生成时，在相同输入和种子下得到相同结构。

### 常见坑

- 用一段总结代替原始材料，主体看不到细节。
- 把研究者标注的条件写进公开表或主体属性。
- 网络边和主体 id 对不上，运行时才报错。
- 数据更新后没有换新 run，旧结果和新配置混在一起。

## 第 7 步：小规模试跑

### 做什么

先跑一个能产生一个可解释对照的最小实验：

- 减少主体数量，但保留至少一个对照群体。
- 减少 tick 数，但保留干预前后。
- 保留真实行动、完成条件和测量，不要为了快而关掉机制。
- 先看 `check`，再看 `run start` 的状态，最后读 `run result`。
- 如果 run 被中断，先看完整点和失败原因，再决定 resume 还是新建。

```sh
society0 check --profile profile.json --json
society0 run start --profile profile.json --dir runs/pilot-001 --ticks 4 --detach --json
society0 run status --dir runs/pilot-001 --json
society0 run result --dir runs/pilot-001 --json
```

### 产出物

- 一次试跑的目录、状态和结果。
- 一张“预期—实际”检查表：主体看到了什么、行动是否发生、状态是否改变、测量是否写入、失败和预算耗尽在哪里。
- 一份下一轮修改清单，只列会改变解释的修改。

### 判断标准

- 主体看到的是设计中的材料，不是研究者的结论。
- 必需行动有成功回执；只有受理没有完成不算完成。
- 环境后果按设计发生，记录能重算结果。
- 失败原因能归到提供方、配置、数据或领域规则，而不是“跑完了但不知道发生了什么”。
- 结果差异的方向和大小可以被下一条对照检验。

### 常见坑

- 第一次就跑几百个主体，最后只能看一个总数。
- 把 `completed` 当成“研究结论成立”；它只表示运行完成。
- 看到模型自述的理由就停止分析，不检查行动记录。
- 失败后直接改测试或删机制，而不是先保留现场和原始错误。
- 试跑后同时改多个地方，下一轮无法判断是哪一处起作用。

## 一页检查表

```text
[ ] 研究问题能对应一个比较和一个结果变量
[ ] 因素表写清了改变、固定和不研究
[ ] 主体层只包含真正感知、决定、行动、承担后果的实体
[ ] ODD 写清了 tick、阶段、暴露、行动、随机性和测量
[ ] profile 通过 check，机制能指到具体插件
[ ] 数据有来源，主体可见与研究者标签分开
[ ] 试跑保留了对照、行动和测量
[ ] 结果能从记录重算，失败和缺失有标记
[ ] 结论范围小于或等于设计能支持的范围
```

## 和因果比较的衔接

试跑稳定后，不要直接扩大规模。先确认哪一个因素最值得单独改变，再按 [causal-branches.md](causal-branches.md) 从同一起点做对照。试跑的作用是证明环境、暴露、行动、记录和测量能工作，不是证明研究假设。

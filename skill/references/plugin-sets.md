# 插件集选择与装配

把已选定的研究机制落实为可执行组合时，按“选择插件集 → 补齐依赖 → 绑定服务 → 对齐时空与状态 → 添加或替换 → 验收”推进。本指南产出装配清单，供构建、开发和恢复使用；研究确认与执行授权沿用主 Skill。外部插件目录是可选的设计资料，已有源码、公开配方和实际接口足以开始。

## 一、选择

先选择能覆盖“可见信息 → 行动 → 环境兑现 → 观察”的典型插件集，再按研究问题增加能力。从[安装准备](<installation.md>)定位 Core 源码根 `$SOCIETY0_REPO`，读取其中 `docs/core-next/builtin-composition.md` 的公开配方。下文的仓库路径同样从这个源码根读取，Skill 独立安装后继续沿用此定位方法。

### 1.1 按实际需要选择起点

- **规则实验：**选择规则配方、主体记录、授权函数、领域机制与日程。普通规则路径保持轻量，模型、记忆和shell按真实消费者加入。
- **模型实验：**在模型配方之外显式绑定模型服务、认知来源和领域机制；核对完整会话，以及所选记忆写入、召回和主动工具。
- **领域组合：**使用已有领域配方时，列出保留、移除和新增成员，核对其工厂实际接受的配置。领域业务规则由扩展提供，Core负责公共装配与执行。

外部目录可能以领域、底层能力或学科分类；这些标签用于发现候选。若采用 `implemented / specification / recipe` 状态，分别核对源码符号、待实现合同和组合成员。`assembly` 表示进入装配的准备程度，组合是否通过验证由实际证据说明。主 Skill 中的“已有可用 / 需要装配 / 需要新建 / 当前不支持”继续表达本任务的判断。

### 1.2 建立装配清单

每个成员填写一行：

| 项目 | 必填内容 |
| --- | --- |
| 选择依据 | 研究作用、保留或新增理由、当前实现与验证范围 |
| 实现定位 | 源码工厂/符号、插件实例名、提供的服务名 |
| 配置消费 | 值与来源、单位/边界、实际读取它的构建器或服务 |
| 依赖绑定 | 直接数据前置、直接服务前置、角色到服务引用的映射 |
| 组合语义 | 业务时点、空间范围、状态所有者、输入输出与阶段位置 |
| 验收入口 | 字段白盒断言、组合检查、适用的恢复与外部服务证据 |

自然语言配置和目录DSL表达设计意图。把每个字段落实到工厂参数、领域初态、动作输入或Schedule消费者；仅写进JSON或提示词无法产生相应的环境规则。无法定位消费者的字段列为实现缺口，避免加入无效果的公开配置。

## 二、装配

逐项落实依赖、服务与时空语义，直至所有必需接口都有提供者。预检依据是实际构造的Plugin集合，目录名称只帮助定位。

### 2.1 分图补齐依赖

递归展开所选配方及静态子插件，可选依赖在功能启用时纳入。分别检查如下关系，保留各自含义：

| 运行声明 | 检查动作 |
| --- | --- |
| `includes` | 静态展开Plugin实例；共享子实例声明一次，避免同名重复。父插件借用子服务仍需声明直接依赖。 |
| `schema_requires` | 检查数据准备与初始化的先决插件及其闭包，单独检查缺失和环。 |
| `requires` | 检查服务安装的直接前置及其闭包，单独检查缺失和环；消费者退出后才释放提供者。 |
| 显式 `Phase` | 将配对后发言、交付后观察等因果顺序写入Schedule；安装顺序无法代替业务计划。 |

`Plugin.schema` 是SQL DDL序列。外部目录中名为 `schema` 或 `requires` 的关系需按其合同翻译，不能直接套用Core同名字段。步骤before/after钩子按依赖安装顺序登记，变更服务边时同时检查钩子顺序。具体合同从源码根的 `docs/core-next/plugin-contract.md` 和 `docs/core-next/composition-contract.md` 读取。

### 2.2 绑定服务与替换槽

把业务角色解析为 `(plugin_name, service_name)`，再传入真实工厂。`ctx.require` 使用的目标必须是消费者显式声明的直接 `requires`；传递依赖中的服务也须显式声明后才能借用。目录ID、业务角色、实例名和局部服务名分别记录，避免混用。

先核对替换槽的输入、输出、错误、状态副作用和资源生命周期，再安装替代实现并更新消费者引用。槽名称或 `accepts` 列表是设计合同，实际接入依赖工厂参数及服务接口。替换可能涉及初始化消费者、信息/动作注册、表名和阶段调用；修改后重新检查闭包。同类机制多实例使用明确实例名、表前缀及信息命名空间，仍可共享主体身份。

### 2.3 对齐时空与状态

1. **时间：**明确单位、激活触发、观察频率和边界归属；将不同粒度映射到同一业务时间线。Moment.time承载业务时点，Session.step承载完整步骤编号，网络等待不推进模拟时间。
2. **空间：**明确地点、网络、辖区或坐标及其ID映射。Core没有统一空间API，空间状态与跨边界交换由领域机制实现；邻接关系、可见性与行动资格分别定义。
3. **状态：**逐项指定权威事实的唯一所有者与规范写入器，列出读写关系。同一领域事件在事务内同步维护事实、投影及索引；主体私有资料、共享事实和研究者测量分别保存。缓存保持可重建。
4. **顺序：**共享冲突状态默认串行；`independent`需要行动顺序无关的领域依据。若全部主体应依据同一开场材料，用 `Phase.prepare` 返回不可变材料并消费 `session.prepared`；其他信息请求仍遵循自身版本合同。

执行语义从源码根的 `docs/core-next/runtime-contract.md` 读取；领域状态与信息的接线参照[环境设计](<environment-design.md#从双机制例子构建自己的世界>)。

## 三、开发

复用与新建沿同一装配清单推进。已有工厂覆盖所需合同就直接装配；缺失合同先写失败用例，再补实现与消费者。

1. 写清机制接受什么输入、何时改变哪些事实、提供哪些信息和动作、怎样表达失败或等待。
2. 声明自身schema及数据前置，准备外部资料时使用 `prepare` 产出同步初始化函数。运行服务通过 `install` 注册，资源取得后立即登记清理与必要的任务收束。
3. 为每个公开字段指明实际消费者，选择可产生可观察差异的输入，先验证字段到消费者的映射，再检查领域结果。
4. 将实现接入原配方，验证新旧消费者的接口、权限、状态不变量及业务顺序；接口变更同步更新受影响调用方。

**短例：社交排序替换。** 从 `social_plugin` 开始，检查其已包含的子插件，避免重复安装默认叶。选择时间倒序时，显式提供 `chronological_ranking_plugin`，将其 `('实例名', 'rank')` 传入 `ranking`；实际模型感知另接 `social_source_plugin` 和 `cognition_plugin`。先用固定候选、关系与时点断言排名，再核对真实呈现与曝光确认。默认关注权重影响排序，严格沿关注边传播需补候选和读取合同。接线依据从源码根的 `docs/core-next/social-contract.md` 读取。

**短例：生产与税务扩展。** 先定位领域提供的生产、库存、交付、税务与账务服务，将依赖与角色映射到实际实例。声明实物来源和税位由谁维护，并将生产推进、交付与观察安排到业务阶段；交付中需要共同兑现的库存、税务和账务事实经同一规范写入边界完成。通过一笔有明确来源的业务检查数量、成本与税务结果。Core只提供公共事务、服务和调度接口，具体税法和行业编译由领域实现。

## 四、验收

装配验收区分静态关系、初始化、字段作用、业务组合及外部服务。每项结论附其实际执行范围，避免把预检成功升级为完整运行证据。

### 4.1 分层验证

- **静态预检：**使用 `PluginHost.describe_plugins()`查看展开后的关系，人工或确定性检查对照清单。该方法返回描述；缺依赖、环和重复实例检查由Host安装与compose执行。两个依赖图分别有效，服务名也须真实存在。
- **组合初始化：**在独立目录通过 `compose` 建根，验证准备与初始化、实际服务解析、失败清理；PluginHost单独安装不执行schema和初始化。
- **字段白盒：**用有效值变化及相关边界断言输入构建器、FoV、领域服务或Schedule，不调用模型。示例值、真实默认与必填输入分别记录。
- **业务组合：**通过实际消费者跑代表性的完整步骤，核对权限、逐笔事实、因果顺序和观察结果；新增或替换机制完成相关确定性检查后，执行受影响组件要求的确定性全量验证。
- **模型与外部资源：**实际使用LLM、嵌入或记忆链且其接线需验证时，选择代表性组合和获准端点检查真实请求、动作、完整Thread及恢复。纯规则和算法字段采用相应确定性证据，无需让每个插件分别调用真实模型；仍适用的端点证据可复用。

### 4.2 恢复与交付

从可信完整步骤在新目录恢复。`compose`核对源schema，跳过 `prepare/initialize`，再安装服务重建本次资源；新增状态依赖初始化时应重新建根，或走另行设计并验证的变更路径。schema匹配后仍需检查冻结输入、业务语义与既有历史是否相容。失败步骤保留诊断，选择首次受影响之前的可信完整点；正常退出插件上下文不会代替Runtime发布完整步骤。

完成后交付装配清单、实现与配置入口、实际检查结果、可信完整点及剩余缺口。清单中的每项公开字段都有消费者、每个必需服务都有提供者、每个领域事实都有写入所有者，后续构建与恢复便可沿同一依据继续。

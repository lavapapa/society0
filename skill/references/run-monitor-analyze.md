# 运行、观察与分析

## 一、先看运行事实

每次运行后，先回答：

- run 是否完成？`state` 和 `lastReason` 是什么？
- 完成了多少 tick？是否达到预设上限？
- 有多少激活完成、失败、等待或未完成？
- 哪些预算先用完：请求、工具调用还是轮次？
- 失败发生在哪个阶段，原始错误是什么？
- 运行耗时、数据库和进程资源大致如何？

```sh
society0 run status --dir <run-dir> --json
society0 run result --dir <run-dir> --json
```

不要先看结论再看运行事实。一个“完成”的 run 也可能有大量失败激活；一个“失败”的 run 也可能已经产生了可用的完整点。

## 二、读取结果

`run result` 给运行级摘要：

- `result.status`、`result.cut`、完整点 frontier。
- `activations.total/completed/failed/byReason/limits/failures`。
- 失败激活的主体、时点、原因、错误码和阶段。

需要更细的业务数据时：

- **主体属性**：用宿主 `observation` 服务查询主体表，或使用发行包的观察脚本重新打开 run。分叉脚本的输出里也包含 `observation.rows`。
- **行动回执**：查询 `action_receipts`，看谁在什么时点做了什么，成功、拒绝、等待还是未完成。
- **公开表**：通过 `public` 挂载读取研究侧公开数据。
- **测量表**：通过 `measurements` 登记和 `measurementRepository` 分页读取；大字段按引用读取完整正文。
- **Thread**：读取主体实际看到的材料、消息和工具调用序列；不要把展示截短当成原文。

CLI 的 `run result` 不是全量数据导出。需要任意表查询时，写一个宿主侧读取脚本，或使用发行包附带的观察入口。

## 三、定量分析

每个解释都要对应实际做过的比较：

- 组大小、条件、观察时点和完成数。
- 结果变量的分布，不只报均值。
- 差异的方向和范围，以及失败、未完成和预算耗尽的比例。
- 多个种子或重复运行之间是否稳定。
- 模型、提供方、提示、预算和温度是否在条件之间保持一致。

常见检查：

- 随 tick 的趋势。
- 处理组与控制组的差异。
- 主体类型或群体差异。
- 缺失、失败和未完成。
- 重复运行的方差。
- 推荐研究中的推荐池大小、评分权重、剪枝阈值、展示条数和曝光记录。

### 先报告比较，再解释机制

一个稳妥的顺序：

1. 这次比较的是什么？
2. 每组有多少个独立运行、多少个主体、多少个 tick？
3. 观察到的值、范围和不确定性是什么？
4. 哪些差异在重复中保持方向？
5. 可能的机制是什么？
6. 还有哪些替代解释？
7. 下一次比较如何区分？

模型自述的理由是定性线索，不是因果证据。多个主体提到同一个线索，也不证明这个线索导致了结果。

## 四、定性分析

LLM 仿真会产生重要定性材料：

- 主体写出的理由。
- 生成的帖子、回复和消息。
- 引用或提到的记忆。
- 访谈回答。
- 失败、拒绝和意外案例。

可以归纳编码，但研究者要审查类别。不要让另一个 LLM 在没有审计的情况下替你做实质解释。

## 五、成本与资源

区分：

- 模型等待时间。
- 工具执行时间。
- 领域计算时间。
- 权威存储和产物写入时间。
- 展示和导出时间。
- 进程内存和 RSS。

嵌套阶段的计时可能互相包含，不要直接相加当成独立成本。未知值不要推算为零。范围读取、按需字段和引用正文保留完整内容的继续访问路径；显式全量分析仍按实际读取量计成本。

## 六、分支比较

分叉目标没有 CLI 的 `entry-status.json`，所以：

- 用分叉脚本输出的 JSON 读取 `targetPoint`、`observation`、`receipts` 和 `result`。
- 需要重新打开时，用 `run-profile.mjs --reopen --observe`，并显式给出源 lineage 目录和 identity。
- 不要把 `society0 run result --dir <目标目录>` 的 `RUN_NOT_FOUND` 当成运行失败。

比较时保持同一口径：

- 同一主体、同一业务时间、同一测量题项。
- 同一 tick 数或同一完整点序号。
- 同一失败和未完成口径。

## 七、报告结构

建议：

1. 研究问题。
2. 设计：主体、环境、条件、tick 定义、测量。
3. 运行：独立运行数、种子、完成数、失败和预算。
4. 定量结果。
5. 定性模式。
6. 稳健性检查。
7. 限制和下一步。

报告里始终写清：

- 这是模拟输出，不是经验观测。
- 模型、提供方、提示和采样带来的依赖。
- 样本、种子和重复的边界。
- 哪些结论可以从记录重算，哪些是研究者的解释。
- 下一次比较要改变什么、固定什么。

## 八、常见误读

- `completed` 只表示运行完成，不表示研究假设成立。
- 主体没有行动，不一定是“主体选择不行动”；也可能是行动不可用、预算耗尽或完成条件未满足。
- 业务拒绝不是执行故障；前者是世界规则不允许，后者是插件、存储或传输出了问题。
- 结果差异很小，也可能是真实差异；结果差异很大，也可能来自一个失败样本。先看分布和失败率。
- 一个种子的方向不能当成稳定机制。

# 记忆与检索

Memory 保存主体自己的经验，使后续激活能够按查询取回相关内容。完整 Thread 记录当时发生的交互，Memory 保存可再利用的经验，两者通过提取作业和原输入水位关联。

## 一、三种行为独立配置

| 策略 | 发生时机 | 对研究的影响 |
| --- | --- | --- |
| `auto_write` | 成功或正常等待的激活之后 | 是否自动把经历转成经验 |
| `auto_recall` | 激活的认知准备阶段 | 是否自动把相关经验加入输入 |
| `active_tools` | 主体发现与调用记忆行动时 | 是否允许主动记住、查询、更新、删除 |

自动召回关闭，已经写入的经验仍保留，主动检索可独立启用。自动写入开启的 decision 需要有效提取器；interview 默认跳过自动写入，同时保留独立召回策略。

策略可以由 `policy_selector(session)` 为每次激活返回，并在激活开始时固定。当前选择留在 Thread 中，便于解释同一主体在不同阶段获得了什么能力。

## 二、原文和索引各自负责什么

SQL 保存正文、用户 metadata、原始向量、版本和作业回执。Chroma 根据这些事实提供候选检索，是可重建的派生资源。恢复后重新建立索引，还应核对候选身份、原文与最终召回结果。

向量相似度负责寻找候选，时间衰减与重要性参与后续排序。未被当前查询召回的记忆仍然保留。研究者应检查实际进入 Thread 的原文，判断它是否与当前问题相关、是否影响了主体决定。

现有检索和索引同步包含同步库调用，历史召回还需要重建相应历史候选集。方法名是 async 时，内部所有计算也未必都离开调用线程；长期运行的资源预算应按实际负载测量。

## 三、经验时间与可见时间

某主体在第 8 步记下第 3 步的一件事，可以同时表达两个时间：`timestamp` 描述经验时间，`visible_step` 描述写入可见时间。这样历史查询不会提前取得尚未写入的经验。

默认激活策略使用 `Session.step` 作为可见版本和衰减序号，单位为完整步骤。`Moment.time` 可以保存日期字符串或其他业务时间；特殊业务日历需要显式策略表达。

更新和删除维护当前投影，并保存相应旧版本。查询当前状态沿活动投影检索；显式历史查询的工作量随相关历史增长。恢复分支以新运行身份隔离后续修改。

## 四、写入作业为何需要身份

自动提取绑定原 Thread 和输入消息水位。相同输入重试复用作业，新增输入产生新水位。提取结果、嵌入、SQL 向量写入、索引同步和完成回执各有明确位置，失败后可以判断哪些工作已经完成。

已完成回执描述原操作。之后更新或删除记忆，原提取作业仍保持完成，避免重新执行时把已处理经验再次写入。未完成步骤中的作业作为诊断保留，恢复继续依据所选完整边界。

需要迁移当前有效经验时可使用 export/import_records，保留原文与原向量；完整历史的迁移沿存储恢复。具体 API 与成本见[记忆参考](../reference/memory.md)，三开关对照可从[记忆教程](../tutorial/memory.md)实际观察。

# 完整步骤与恢复

运行中可以及时看到已提交的消息、决定和诊断，而恢复需要一个更强的边界：本步骤要求完成的机制工作、主体任务与关联工件已经收束。这个边界由完整步骤身份表达。

## 一、短事务与整步完成

规范写入器使用同步 SQL 事务更新事实、投影与索引。单个事务结束后，其他读取者可以看到新状态；一个步骤可能包含很多短事务和外部请求。

Runtime 等待阶段激活及 after-step 钩子完成，再发布完整步骤。SQLite Session 捕获净行变化，存储将变化集与工件引用准备好，最后发布不可变步骤描述符。描述符是完整身份的权威来源。

当前数据库的 `complete_step` 是已经确认的完成下界；描述符发布与辅助水位更新之间存在窗口。Observation 分别显示 complete、下界与 live_revision，让调用者知道自己看到哪一种事实。

## 二、失败留下什么

若主体工具处理器、领域钩子或权威写入发生异常，Runtime 停止阶段，取消并等待工作清理，随后废弃当前未完整状态。已经提交的短事务和 Thread 保留为诊断，当前实例拒绝继续写入和发布。

SQL 事务可以回滚本事务内的变化。数据库之外的网络调用、外部文件或其他 Python 副作用需要其拥有者处理；恢复可能重新执行完整点之后的外部请求。因此研究或领域插件应明确哪些操作可重复，以及外部结果怎样留证。

预算耗尽的 DriverResult 默认使步骤失败；明确选择 `incomplete="collect"` 的阶段可以保存未完成结果。处理器与存储异常始终沿失败边界传播。

## 三、恢复、分叉和分析

| 目的 | 入口 | 目标目录的性质 |
| --- | --- | --- |
| 从完整点继续执行 | `restore`，或 runner 的 `source/step` | 新运行身份，可继续写入 |
| 从共同历史比较后续条件 | 从相同完整点分别恢复 | 各自独立运行，保留来源 |
| 固定历史点供检查 | `prepare_readonly` | 只读分析目录，保留选定完整身份 |

恢复从 root 与所选完整变化链重建，使用新目录，随后重新装配服务。输入或机制变化需要按恢复合同核对；初始假设改变且影响共同历史时，应创建新根运行。

只读分析目录用于查询 Thread、记忆权威数据、结果与封存数据集。它省去可执行分支的新 root，既不供 writer 打开，也不作为后续恢复来源。临时或持久分析的目录生命周期由调用方选择。

## 四、存储成本与可信性

热步骤发布保存变化增量；冷恢复包含 root 和变化链的物化成本。巨大的行修改仍会产生相应捕获成本，因此机制应把冷热字段分开，并采用明确记录边界与索引。不可变工件必须通过引用进入完整描述符，准备但未引用的文件由离线清理处理。

完整点说明软件完成了规定的发布流程。研究者还需判断其中的历史是否可信：输入错误何时开始影响主体认知，后续决定又受到了哪些影响？选择最近的完整点与选择最近的可信完整点，是两项需要一起完成的判断。

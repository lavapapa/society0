# 并发的三个层次

一个实验可能同时等待多个模型请求，也可能计算一张大图，还可能让主体修改共享事实。这三种工作对应不同约束。分别配置它们，才能在保持业务顺序的同时利用外部服务与计算资源。

## 一、主体能否同时行动

阶段默认 `execution="serial"`，容量为 1。同批主体按提交顺序执行，后面的主体可以看到前面已经写入的 live 事实。这适合顺序会影响结果的交互。

独立阶段声明 `execution="independent"`。有效容量优先取 `Phase.capacity`，其次取 `Runtime.capacity`；同一主体的串行键继续生效。独立性由机制和研究设计保证，Runtime 不会自动证明共享写入可交换。

例如，互不影响的问卷测量可以在同一阶段并行；争夺最后一个名额的报名行为需要明确先后或单独的分配机制。把容量调大，可能改变主体看到的世界，因而是一项业务语义选择。

## 二、外部服务能接多少请求

模型和嵌入提供方分别限制实际物理请求。端点有自己的容量，profile 可有总许可，多个 profile 还能共享 `request_limit`。主体即使已经获得激活槽位，也可能等待提供方许可。

| 配置 | 控制的工作 |
| --- | --- |
| Phase / Runtime capacity | 同时执行的独立主体激活 |
| endpoint concurrency | 某一端点上的物理请求 |
| profile global_concurrency | 某个提供方配置的总请求许可 |
| shared request_limit | 多个模型或嵌入配置共同使用的许可 |

嵌入可以把多位主体的独立文本合为一个物理请求，每段返回向量仍回到原主体。缓存命中和批次等待具有各自计量；共享物理批次的按主体用量存在重复归属，跨主体求和会重复计算。

## 三、CPU 计算怎样交给进程

`ProcessCompute` 为同一运行提供有界 spawn 进程池。机制提交可序列化的紧凑输入，计算函数返回结果；主线程再按业务顺序安装到权威状态。

进程池的 `max_workers` 限制工作进程，`max_pending` 限制已提交且未完成的任务。输入批次的字节量与调用方驻留仍需控制；数据库连接、运行对象和可写共享状态留在拥有者一侧。

取消等待者后，正在计算的进程任务可能继续运行。额度在原生 future 完成后归还，关闭等待已启动计算结束。这是故障收尾可能较长的一个原因。

## 四、怎样选择配置

先说明哪些操作的顺序影响研究结果，再选择阶段执行方式。随后依据实际端点能力设置请求许可，把可分离的纯计算交给共享进程池。结果中记录的 `capacity` 与 `concurrency_source` 可确认阶段实际采用了哪一级配置。

耗时分析分别观察领域计算、请求排队、提供方等待、记忆与持久化。减少信息或行动会改变实验条件，应单独作为研究变量处理。具体装配与测量入口见[并发指南](../guide/parallel.md)和[诊断参考](../reference/diagnostics.md)。

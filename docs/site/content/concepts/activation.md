# 主体与激活

主体身份贯穿整个研究，一次决定却只在一小段时间里执行。Society0 把前者放进持久目录，后者交给 Driver 和 Session 组织。分清这两件事，才能回答几个实际问题：资料在什么时候被读到、这次操作以谁的名义进行、哪些状态必须存下来才恢复得了。

## 从目录里的一条记录到一次决定

`ActorRecord` 保存 ID、驱动标签、persona、state、config、roles 与 active。ActorDirectory 提供这些数据，ActorStore 把记录里的持久驱动名称解析成当前安装的工厂。worker 真正要用到某位主体时，才取出这条记录的视图并构造 Driver；没有激活的主体不必各自占着一个驱动对象。

目录按条件返回符合要求的 ID。是否激活由阶段决定，具体的业务资格由机制判断。拥有 `organizer` 角色便于挑出组织者；这位主体能不能发出某条消息，还要对话机制确认它的成员身份与当前配对。

激活时，Runtime 创建绑定该主体的 Session，把信息、行动、当前 Moment、共享准备值与信号一并交给这次会话。这次交互结束、失败或被取消之后，交互作用域关闭，借出去的门面随之失效。等待中的事项或主观状态如果以后还要用，就得保存到目录或者机制状态里。

## 步骤、业务时间和 Moment 各自表示什么

| 身份 | 用途 | 示例 |
| --- | --- | --- |
| `Session.step` | 正在执行的连续完整步骤编号 | 1、2、3 |
| `Moment.time` | 研究者定义的业务时间 | 轮次、日期字符串、其他 JSON 时间表示 |
| `Moment.phase` | 当前阶段语境 | `talk`、`interview` |
| Thread 身份 | 同主体、同 Moment、同 mode 的交互 | Alice 在某轮讨论中的 decision |

网络等待会拉长真实运行时间，业务时间仍由 Schedule 决定。同一个 Moment 里可以反复激活：新信号进来之后，再次调用这位主体的 Driver。LLM 的持久 Thread 接着上一次的交互往下走，各认知来源靠自己的位置判断哪些是新增内容。

临时的 Session 不保存全部历史。A→B→A 这样来回的 Thread 与消费位置怎么恢复，由持久服务负责，细节见[认知专题](cognition.md)。记忆默认用整数 step 管理可见版本和衰减，业务日期保留它原本的含义。

## 同一个主体的多次信号怎样合并

`activate` 提交一个针对某位主体的信号。这位主体还在等待时，新信号并进同一次激活；它正在执行时，新信号留到下一次激活。Driver 从 `session.signals` 取得本轮的载荷，所有实际工作都在阶段结束前排空。

同一位主体在同一时刻只有一个 Driver 写者，独立阶段也保留这条约束。`drain` 取回尚未消费的结果，按主体首次提交的顺序和激活 round 排列，网络返回的快慢不会改变结果的次序。

## 怎么读 DriverResult 的状态

| DriverResult 状态 | 对步骤的含义 |
| --- | --- |
| `completed` | 本次决定完成 |
| `waiting` | 正常暂停，允许开放事项随完整步骤保存，后续信号可再次激活 |
| `incomplete` | 本次决定未完成；默认使步骤失败，显式 `collect` 阶段可收集其真实状态 |

动作自己的 `accepted/completed/rejected` 描述业务请求；DriverResult 描述整次激活。请求被拒绝之后主体可以接着做别的决定，请求受理了也可能还要等后续过程。预算用尽或输出被截断，都要把未完成的原因留下来。

领域处理器、Thread 写入等执行异常都会使步骤失败；`collect` 处理的是返回的 incomplete。配置与实践见[调度指南](../guide/schedule.md)和[主体教程](../tutorial/actors.md)。

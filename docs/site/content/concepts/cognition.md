# 完整会话与增量认知

主体第二次被激活时，两件事必须同时成立：之前拿到的材料还在，这次新增的信息也进得来。前一件由完整 Thread 负责，后一件由各来源记下的位置负责。同一时点里反复做决定、进程重启之后接着跑，都要靠这两件事配合。

## 一次完整输入里有哪些内容

`CognitiveInput` 把 persona、环境说明、感知精度、当前主观状态、信号和提醒组织到一起。稳定的背景第一次就进入 Thread，之后只有实际内容改变才追加新原文；当前状态与本轮材料每次都随激活进入。

Thread 保留此前的完整消息和 typed 提供方响应。增量感知减少了重复追加的材料，已经在上下文里的内容照样参与模型请求。文件空间中的 `/context/messages.json` 是给主体查阅用的入口；真正必要的输入仍然沿驱动进入完整 Thread。

主体读到的材料与客观世界是两件可以分开检查的事。环境里可能已经产生了一条消息，而这位主体还没拿到它；要判断某次决定依据的是什么，研究者需要检查实际发生的输入事件。

## 多个来源各自记录读到哪里

一位主体可能同时接收社交推荐和通知。`SourceSpec` 给每个来源一个稳定的 ID，以及显式的服务引用。组合器按声明顺序读取，把材料拼接起来，同时分别保存各来源读到的原始位置。

首次消费的 `previous` 为 `None`；保存过的合法空位置用 `SourcePosition(None)` 表达。合法的 `0`、空映射也保留原值。这样来源能区分“第一次读取”和“已经读取到一个空位置”。

暂时省去某个来源时，旧位置仍然保留，以后重新加入可以接着读。改变一个 ID 所代表的位置含义时，应该分配新 ID 或者创建新运行，免得用旧游标去解释新的协议。来源的选择与顺序属于研究配方，需要记录下来。

## 为什么曝光要等到消息保存之后才登记

假设读取推荐的同时要更新曝光次数。构建器可能读了两个来源，最终却选了另一批输入，也可能在写入 Thread 时编码失败。如果在读取那一刻就把曝光记下来，环境事实就会宣称主体看过一份实际没有保存的材料。

`InputBatch.effects` 把这些确认放在明确的边界之后：

```text
读取来源 → 选中最终批次 → 保存消息与全部位置 → 执行 effects → 请求提供方
```

消息与消费位置在同一个 Thread 事务里保存。被丢弃或保存失败的批次没有呈现确认。effects 自身仍可能失败：已经保存的输入留作诊断，Runtime 决定这一步能不能发布，恢复时选择此前可信的完整点。

社交 source 在这里确认实际曝光；纯推荐预览和独立排名 observer 仍按读取处理。通知也可以在保存输入之后登记收件确认。

## 扩展挂进这条流程的哪个位置

ActivationContext 让一系列有序扩展共用本次的认知、只读挂载和 experience。扩展挂上之后，构建器才开始产生输入；需要已保存输入的准备工作往后排，退出时按相反顺序清理。MemoryExtension 就在这条流程里加入召回，并在激活成功之后写入记忆；规则驱动也能提供自己的结构化经历。

自己搭多来源认知时，先想清楚每个来源的位置表示什么、什么时候确认，再按[认知指南](../guide/cognition.md)把它们组合起来。想看清实际原文、游标和 Thread 之间的关系，可以运行[模型教程](../tutorial/llm.md)里的离线例子。

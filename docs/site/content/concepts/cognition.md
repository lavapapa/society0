# 完整会话与增量认知

主体再次被激活时，需要保留已经取得的材料，并看到这次新增的信息。完整 Thread 与增量来源位置分别负责这两件事。它们共同支持同一时点的多次决定，也支持跨进程恢复。

## 一、完整输入包含什么

`CognitiveInput` 组织 persona、环境说明、感知精度、当前主观状态、信号和提醒。稳定背景首次进入 Thread，之后若实际内容改变则追加新原文；当前状态与本轮材料随激活进入。

Thread 保留此前完整消息和 typed 提供方响应。增量感知减少重复追加的材料，已存在上下文继续参与模型请求。文件空间中的 `/context/messages.json` 给主体提供查阅入口；实际必要输入仍沿驱动进入完整 Thread。

主体读到的材料与客观世界是两个可分别检查的对象。环境可以已经产生一条消息，而该主体尚未取得它；研究者需要检查实际输入事件，才能判断某次决定依据了什么。

## 二、多来源各自保存位置

一个主体可能同时接收社交推荐和通知。`SourceSpec` 给每个来源一个稳定 ID，以及显式服务引用。组合器按声明顺序读取，拼接材料，同时分别保存各来源的原始位置。

首次消费的 `previous` 为 `None`；保存过的合法空位置用 `SourcePosition(None)` 表达。合法的 `0`、空映射也保留原值。这样来源能区分“第一次读取”和“已经读取到一个空位置”。

暂时省去来源时，旧位置仍保留；以后重新加入可以继续。改变一个 ID 所代表的位置语义时，应分配新 ID 或创建新运行，避免用旧游标解释新协议。来源选择与顺序属于研究配方，需要记录。

## 三、为什么呈现效果延后

假设读取推荐会更新曝光次数。构建器可能读取了两个来源，最终却选择另一批输入，或者写入 Thread 时编码失败。若读取时已记曝光，环境事实就会宣称主体看过实际未保存的材料。

`InputBatch.effects` 把这些确认放在明确边界之后：

```text
读取来源 → 选中最终批次 → 保存消息与全部位置 → 执行 effects → 请求提供方
```

消息与消费位置在同一 Thread 事务保存。被丢弃或保存失败的批次没有呈现确认。effects 自身仍可能失败：已保存输入留作诊断，Runtime 决定该步是否能够发布，恢复选择此前可信完整点。

社交 source 使用这个边界确认实际曝光；纯推荐预览和独立排名 observer 保持读取语义。通知也可以在保存输入后登记收件确认。

## 四、扩展怎样参加

ActivationContext 让有序扩展共享本次认知、只读挂载和 experience。扩展进入之后，构建器产生输入；需要已保存输入的准备工作延后执行，退出按逆序清理。MemoryExtension 在此流程里加入召回与成功后的记忆写入，规则驱动也能提供自己的结构化经历。

搭建自己的多来源认知时，先定义每个来源的位置与确认语义，再按[认知指南](../guide/cognition.md)组合。想观察实际原文、游标和 Thread 的关系，可运行[模型教程](../tutorial/llm.md)中的离线例子。

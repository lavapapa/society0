# 共享环境与机制

一次 Society0 运行把主体放在同一个共享环境里。机制插件负责环境内部的规则与事实，主体通过信息和行动接口参与。把这些职责分开，才能解释一个主体的选择怎样改变另一个主体随后面对的世界。

## 一、同一组主体可以参加多个机制

在[对话教程](../tutorial/conversation.md)中，四位主体同时参加 `work` 和 `commons`。两个机制分别保存配对和消息，借用同一份 ActorDirectory，共用同一个 StageStore。`work` 的发信行为影响其收件箱，`commons` 保持自己的当前轮与历史。

一个具名插件可以提供多个服务，例如对话机制提供 `mechanism`，信息插件提供 `information` 与 `actions`。消费者通过 `(插件名, 服务名)` 引用它们。名称决定装配中的定位；主体身份继续由目录保存。

领域机制拥有业务事实及合法写入方式。Driver 可以决定申请什么操作，处理器负责在真实写入边界核验资格，并同步更新事实、当前投影和必要索引。这样规则驱动与模型驱动可以共享同一套约束。

## 二、为什么有两类依赖图

考虑“先登记参与者，再建立对话成员，同时让主体驱动读取对话材料”的情况。初始化数据的先后与服务借用的先后分别由两张图表达：

| 声明 | 它回答什么 | 例子 |
| --- | --- | --- |
| `schema_requires` | 数据初始化前需要哪些插件的数据先准备好？ | 对话成员外键依赖主体目录 |
| `requires` | 安装和使用服务时借用哪些提供方？ | 驱动工厂借用认知输入服务 |
| `includes` | 此配方静态包含哪些子插件？ | 社交配方包含内容、关系、推荐等叶插件 |

`compose` 先建立或恢复共享存储，再安装服务。依赖图各自检查缺项与环；`includes` 展开后的名称需要唯一。既有完整点恢复时，持久数据来自所选状态，服务重新装配，初始记录不会重新插入。

业务执行顺序由 Schedule 与 Phase 给出。例如“先配对、后发信”写在阶段列表中。服务安装早晚仅决定资源可用性，研究者仍需明确每步先做什么。

## 三、资源由谁关闭

创建资源的插件登记关闭动作，借用资源的消费者声明依赖。Information 挂载和 Action 注册返回注销函数，可与资源关闭一起托管；退出时先撤回入口，再释放资源。

运行关闭先排空 Runtime，再收束 worker，最后逆序关闭普通资源。这个顺序保护正在写入的任务，避免模型请求、记忆作业仍在工作时底层连接先被释放。安装中途失败同样撤销已经成功的登记。

一个可复用插件因此需要说明三件事：自己保存哪些事实、借用哪些服务、创建哪些需关闭的资源。具体实现从[插件指南](../guide/plugins.md)开始；选择 preset、叶插件和同名实例的装配方法见[组合指南](../guide/composition.md)。

# 语言与执行层决策

新版采用 Python 公共 Core 与插件接口，优先把大量数据留在 SQLite 及成熟原生库中处理。Rust 是新增自有计算内核的优先语言，TypeScript 用于已有工作台以及确有生态收益的工具适配。此决策由运行负载和现有资产决定，后续性能验收直接检查语言边界是否成为瓶颈。

语言分工继续适用。当前实现按 [技术选型](technology-decisions.md) 使用原生 zstd，同步编码和压缩已替代自有工作池；代码完成与验证状态见 [TODO](TODO.md)。

## 一、负载

Society0 的共同运行过程包含机制编排、主体交互、模型网络等待、数据查询、局部修改、历史保存和自主分析。持久数据规模与常驻 Python 对象规模可以分开。小型插件主机与机制接口不需要承载全部世界记录，网络请求通过异步等待，查询和变化捕获交给 SQLite，压缩交给原生压缩器。

现有实验已经显示，拆分热字段与冷正文对变化捕获内存有决定性影响；同样逻辑搬到 Rust 后，大行旧值仍由 SQLite Session 保存。长读阻碍 WAL 回收也是数据库使用合同的问题。减少全量 World、按主体复制材料和历史扫描，是各语言都需要完成的设计。

当前持久化编码器以独立 64KiB zstd 帧保存在线正文，冷批次使用不可变 SQLite 工件与按 ordinal/chunk 索引的独立 zstd 帧。JSON 通过 python-rapidjson 同步 push 接口编码，规范 writer 同步压缩，保持记录与分块的确定顺序；机制循环与最终写盘分别计时。实际记录子集的编码收益及完整范围见原生 JSON 实验工件，局部加速不作为整步收益。因此公共层采用 Python，并不等于把所有重计算留在 Python 循环里。

## 二、取舍

Python 保留模型、科学计算、网络图、嵌入与研究脚本的直接生态，已有完整模型回合、提供方合同和测试可以提取复用。插件作者无需同时维护 Rust 编译工具链。其代价是对象布局较大、常规解释器上的纯 Python CPU 线程受 GIL 约束，以及大量逐行原生调用的转换开销。新接口采用分页、批量参数和数据引用控制这些边界。

Rust 适合 CPU 密集且输入输出稳定的扫描、解析、压缩或数值计算，能够用紧凑数据与线程实现受控的资源使用。整套插件和模型编排改写为 Rust，会增加异步插件接口、动态加载、研究者开发和已有能力迁移的工作量。目前重计算可由现成原生库承担，尚无证据要求自行重写这些库。若明确热点需要自有实现，使用批量输入输出的 Rust 扩展，避免每个字段跨一次 Python/Rust 边界。

TypeScript 对工作台、网页和 agent shell 工具有直接生态价值。Node worker 可以处理 CPU 并行任务，但任务发送仍需处理对象复制、转移或共享缓冲区；单纯切换到事件循环不会自动并行运行所有机制。把 Python 科学计算资产搬过 IPC 也可能重新造成大对象编码。因此 UI 保留 TypeScript；shell 的生态优势通过小型集成试验衡量后使用。

Python 的 free-threaded 构建提供额外选择，第三方扩展可能重新启用 GIL，内存管理也有不同开销。首版运行环境继续使用已经可验证的常规 Python；以依赖支持与实际 RSS、吞吐对照决定是否另行采用 free-threaded，不能以版本号推断整个程序已能有效并行。

## 三、执行

公共插件 API 传递身份、查询条件、有限结果与明确的数据引用。数据库计算尽量在查询中完成，批量数据转换交给适合的原生库。压缩直接交给原生库；可选共享 ProcessPoolExecutor 承担独立 Python 计算，使用前须计入输入编码、复制、结果合并和进程组内存。共享权威写入按确定顺序提交，多核工作者返回计算结果，不能通过抢占写入改变业务次序。

新增 Rust 模块的触发证据是：长历史与大对象验收中，经过数据结构和查询优化后，仍存在占据主要耗时的纯 Python 计算；该计算具有稳定批量接口，并且原型在完整往返成本与内存下优于现成实现。届时保留 Python 插件 API，替换该计算实现。若压力测试显示协调层本身占据主要成本，再重新审查协调层语言。

另一个实际适用点是成熟原生组件的接口连接。Bashkit 已有 OverlayFs 和稳定名称的文件系统 capsule 协议，当前 Python 绑定未直接提供增量层与动态目录所需的全部接口。小型 Rust 适配器可以委托既有文件系统实现，将必要操作接入 Python 的信息与持久化服务；其价值来自复用现成能力和消除重复全文快照。该薄适配器已接入产品，读、写、删除、重命名、符号链接语义与完整恢复经真实解释器验证；macOS arm64 和 Linux x86_64 wheel 已在干净环境运行。公共插件继续使用 Python，普通规则运行无需创建 shell 或加载该适配器。

工作区当前使用原生 OverlayFs 的文件级 copy-up，未修改文件复用权威路径索引与既有工件。原生单文件读取仍会物化该文件，修改巨文件的成本随文件大小增长。存储、机制计算、模型与记忆、观察和工作区的整体收益按完整负载分别验收；局部多核加速与整步耗时保持各自口径。

官方实现依据包括 [APSW 执行模型](https://rogerbinns.github.io/apsw/execution.html)、[Python free-threading](https://docs.python.org/3/howto/free-threading-python.html)、[Node worker threads](https://nodejs.org/api/worker_threads.html) 和 [Bashkit Python API](https://bashkit.sh/api/python/)。本地实验及其限制见 [存储实验](storage-experiments.md)、[工作区合同](workspace-contract.md) 与 [安装说明](installation.md)，具体原始数据保存在 research/core-next。

# 社交机制

社交插件在同一个共享环境中提供帖子、关系、通知与推荐。一个插件实例对应一个平台，主体身份由 ActorStore 共享；同类多实例使用独立名称和存储表。机制保持领域事实、当前计数与原向量，Chroma 承担可重建的向量检索。

## 一、组合

`social_plugin(members, name='social', config=..., edges=..., seed=..., embedding=..., vector_client=...)` 返回普通 Plugin，自动贡献静态 schema、初始化与服务依赖。`embedding=('embeddings','profile')` 选择嵌入插件的已有提供方，`vector_client=('vectors','client')` 使用声明的客户端服务。关系生成配置沿用有效的五种拓扑模型；显式 edges 可直接提供初始关系。初始化随机源由 seed 固定，恢复读取已保存关系与配置。

推荐配置启用向量相似度时需要提供两项资源。关闭相似度是显式研究配置。正文长度限制来自原社交配置，负一表示不设业务长度上限。它与模型输出预算、Thread 历史保存无关。

## 二、信息与行动

主体通过动态行动发现取得发布、点赞、评论、转发、关注与取消关注。执行时重新核实目标和成员资格。读取帖子、公开资料、热门帖子与消费通知亦有显式行动入口；热门阅读和通知消费含领域状态效果。公开资料含类型、架构、兴趣、心情、社交统计与最近原文预览，私有人格正文留在主体认知范围。

共享路径 `/social/posts`、`participants`、`replies` 支持通用结构化查询，`content/<id>`、`reply_content/<id>` 提供原始正文范围读取。`notifications` 给出当前未读条目，`notification_data/<id>` 保留完整通知内容并核验收件人；消费后原始通知仍可读取。

`/social/feed` 按推荐次序分页返回所有活动候选的分数、帖子 Ref 和正文路径，返回精确总数及继续游标。机制程序接口 `recommended_feed` 按已有配置的 post_count 生成推荐视图。两者共享候选及评分算法；一般字段筛选、排序和抽样使用 posts 路径。推荐游标绑定运行、主体、时点和相关领域表版本，诊断 Thread 写入不会改变该版本。新帖子、关系、认知画像或相关权限变化后需要重新开始读取。

## 三、完整步骤

调度在主体阶段之后调用 `await social.after_tick()`，完成待写帖子向量和本步骤曝光计数、最后推荐记录，再由 Runtime 发布完整步骤。向量正文先进入权威 SQLite，派生向量库水位成功推进后继续使用；恢复保留原始向量并重建派生集合。机制当前没有后台独立推进任务。插件关闭会取消并收束尚在等待嵌入的自有调用，然后依赖资源再关闭。推荐嵌入等待期间源偏好或候选版本变化会明确拒绝该次结果，下一次读取重新取得当前资料。

步骤中断遵循 Runtime 的失败边界。完整检查点保存已完成的曝光、通知消费、关系和帖子；失败步骤恢复到此前完整状态。任何显式外部资源失败继续向运行层传播，调用方据此结束当前步骤。

## 四、工作量

拓扑构造属于初始化；不同算法可能需要二次规模工作。常规点赞、计数和关系维护使用当前索引与同一 SQL 事务，正文冷表独立保存。帖子范围读取使用原生 BLOB 句柄，近期资料预览读取有限字节。

推荐工作量由活动候选数量、配置召回规模、查询嵌入与向量索引决定。候选池保留原有近期、热门和最小存活期语义。分页仍需生成完整候选次序并计算精确总数；最近一次完整偏好、活动候选和向量水位相同时复用语义分数；缓存容量固定为一次查询，页面排序仍按当前评分计算。公开完整资料和逐帖完整详情按请求读取其相关事实，所需信息始终可继续取得。

显式内容干预规则 `intervene` 扫描需要检查的正文，并使用调度提供的随机函数；该成本属于选用该规则的步骤。普通主体行为不会自动执行全历史内容检查。`update_trending_topics` 使用当前热门索引更新短投影。

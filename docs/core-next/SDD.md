# Society0 Core 实施规格

本规格记录 [PRD](PRD.md) 和 [技术选型](technology-decisions.md) 的接口与实施边界。当前先完成代码和独立静态审查，测试执行前停止；后续按消费者及失败窗口验收。[能力对照](capability-parity.md) 管理旧语义，[TODO](TODO.md) 管理当前进度。

## 一、组合

一次运行拥有一个共享环境。环境由插件主机中相互依赖的服务组成，主体激活按需取得带身份和时点的访问作用域。初始化不枚举每个主体能够接触的全部对象，也不为每个主体建立完整文件树。

### 1.1 主机和生命周期

`Plugin(name, requires, install, schema=(), initialize=None, prepare=None)` 的 name 是本次组合内的实例名，同一实现可建立多个名称不同的实例。`PluginHost` 在安装前完成名称、依赖和环检查，按依赖顺序安装。安装器通过 `provide(name, value)` 发布服务，通过 `require(plugin, service)` 使用直接依赖，通过上下文管理器和清理回调注册资源。运行结束、部分安装失败和取消均逆序释放资源。

服务名在所属插件内唯一。实际服务注册发生在安装器内，服务冲突可能在安装后才发现，因此必须清理此前已取得资源；预检的保证适用于插件依赖图。compose 按依赖顺序收集声明的 schema，在同一数据库事务初始化状态后安装服务。需要外部异步读取的插件可选用 prepare 上下文管理器：先准备数据并产出同步 writer 回调，根事务按依赖顺序执行普通 initialize 和准备所得回调，托管已创建的存储后关闭准备资源，再进入运行服务安装。准备闭包及其大数据在进入正式运行前释放；标准上下文管理器承担成功、失败和取消的清理。恢复先验证 schema，再恢复选定完整点，prepare 与 initialize 均跳过。初版不支持运行中装卸，资源生命周期不承担领域写入的撤销。

机制通过安装期的 `on_step(before=..., after=...)` 注册运行钩子，Runtime 在主机就绪后固定本步依赖顺序，按 before、phases、after、complete 执行。关闭采用先停止并排空运行任务、再逆序释放资源的两个阶段；运行可能早于机制安装，因此运行任务的 quiesce 必须先于任何机制资源关闭。关闭本身不触发业务步骤钩子；钩子失败遵守完整步骤失效合同。

### 1.2 代码边界

`society0.kernel.plugins` 只管理组合，`society0.kernel.interaction` 管理引用、作用域、信息和行动合同。持久化、时间、模型与记忆进入相应基础插件模块。公共入口已切换到 Core 与基础插件；旧实现从产品移除，固定 Git 基线及 tests/reference 保留比较证据。

机制插件持有自己的类型和索引定义，可注册信息提供者和行动定义。通用 Core 不包含市场、行业、经济或社交推荐的业务规则。

## 二、交互

共同合同覆盖结构化规则驱动和 LLM 工具驱动。二者通过相同的身份范围查询信息、提交意图、取得反馈，文件与 shell 是该合同的一个呈现层。

### 2.1 引用与作用域

`Ref(namespace, kind, key)` 为不可变值，namespace 对应机制实例，kind 由机制定义，key 为稳定字符串。引用无需加载对象；对象消失由提供者返回明确的不可用结果。路径是引用的呈现，可以改变目录布局而保留领域引用。

`Moment(time, phase)` 保存可序列化的模拟时间和阶段。`InteractionScope(actor, moment)` 由运行时创建，封装有效标记；退出后继续查询或执行抛出作用域失效错误。LLM 的参数中不接收 actor 或研究者权限，工具闭包绑定已有 scope。研究者访问以明确的外部 scope 表达。

访问策略接口为 `allows(scope, operation, ref)`，operation 使用 discover、read、invoke 等有限公共动词，机制按自己的关系和角色事实返回结果。目录枚举先应用 discover，再计算该范围的数量；知道路径仍须独立通过 read。行动发现与执行分别检查 invoke 和业务条件。

### 2.2 信息接口

`Information` 注册按目录前缀负责的信息提供者，目录本身按需枚举。提供者实现 `list(scope, path, limit, cursor)`、`read(scope, path, offset, size)`，数据集额外实现 `query(scope, path, query)`。文档读取返回内容和总字节数、下一位置、版本及来源；列表和数据集返回 `Page(items, total, next_cursor, revision)`。不存在读完首屏即无法继续取得原文的默认路径。

数据查询的首批公共表达覆盖字段选择、范围过滤、排序、分页、最近记录和可复现抽样；提供者明确支持哪些操作，按底层索引执行。大集合不能先转成列表再执行 limit。SQL、向量检索与文档原文保留适合自己的物理布局。逐一实现定制读取工具的职责转为实现一次提供者接口。

一次读取使用短作用域的一致版本。SQL 信息的页版本由自身数据表、明确声明的查询依赖及共同权限依赖的事务水位决定；游标同时绑定运行身份与查询条件。全局 live_revision 单独用于运行诊断。会话记录等无关表的追加不影响正在读取的数据页，相关表发生写入时返回游标已过期，调用者可以重新开始。作用域显式指定 revision 时仍表示要求全局一致快照。持续追加数据使用独立序号游标，读到末尾仍可继续取得新增记录。不得跨模型网络等待长期持有 SQLite 读事务。

表的写入版本由规范写入连接利用 SQLite 原生 authorizer 在语句准备时登记，并在同一事务发布；插件声明读取依赖即可。授权函数、精确计数或跨表条件读取的额外表也属于依赖。此粒度会让同表中无关行的更新使游标过期，这是首版保守边界；后续按实测冲突率考虑更细的分区版本。回滚不发布版本，新运行身份使来源游标失效。

### 2.3 行动接口

`Action(name, target_kind, description, parameters, handler, terminal=False)` 是按类型注册的模板。`Actions.find(scope, target, query, limit, cursor)` 根据目标与范围返回候选，`describe(scope, name, target)` 按需取得完整参数，`invoke(scope, name, target, arguments)` 验证参数、当前访问和条件后调用处理器。注册量由行动类别数决定，不随所有对象的笛卡尔积增长。

行动反馈包括 completed、accepted、rejected；无法维持步骤一致性的执行异常作为故障向调度传播。accepted 可携带持续过程引用，终止行动须 completed 才结束主体决定。发现不能替代执行时的再次判定。跨机制的原子业务改动由同一权威事务涵盖，事务内不得等待模型。调用标识与已执行结果由 Thread/驱动记录，用于区分模型重复调用和传输重试。

### 2.4 工作区与 shell

共享材料以只读信息挂载呈现，主体工作区保存其本人创建的文件。文件操作不隐式写入世界事实。工作区持久化以文件为增量单位，SQL 保存当前路径索引，未改变的正文通过不可变工件复用。激活结束可以释放解释器，后续重建保留文件以及变量、当前目录等 shell 会话状态。

shell 集成 Bashkit，薄 Rust 适配器连接其成熟 OverlayFs 与 Python 信息服务。每次激活创建一个 overlay，私有下层按主体及路径查询共享 SQL 索引，上层保留本次文件变化；下次激活重新查当前索引，避免串接历史 overlay。通用 data 命令把分页、过滤和抽样下推到信息提供者，输出供 jq 等现成工具继续处理。共享大文档通过 manifest/parts 的有界文件呈现，目录按页懒展开；原生接口的整文件读取成本限制在当前分片。完整原文可重组，私有巨文件与完整输出的实际成本分别验收。具体合同见 [工作区](workspace-contract.md)，不自行实现 bash 或任意脚本到 SQL 的编译器。

## 三、运行

运行时负责把主体的决定放在明确的时间和事实边界上。调度的完成条件、持久化的完成条件与模型正常结束相互连接，同时保留独立的诊断信息。

### 3.1 主体与时间

主体记录持续身份、驱动配置和主观状态引用。Driver 接收绑定的交互会话并返回 completed、waiting 或 incomplete 结果。LLMDriver 使用 Pydantic AI Agent.iter 和顺序 Tool 推进模型与工具，领域账本及完整步骤保持独立；typed 消息借用、预算、协议失败与回执接线见 [模型决定合同](llm-contract.md)。规则与 LLM 驱动均可暂停和再次激活；LLM 通过少量 meta tools 发现行动和读取材料，完整 Thread 保存所有实际输入与输出。

Step 调度运行顺序阶段，Phase 调度显式声明阶段参与者、共同可见版本和行动安装顺序。读取批次使用共同版本或明确的顺序可见语义。同一主体同时仅有一个激活写者。independent 阶段中的行动到达时立即执行规范事务，因此跨主体写入先后可能随模型响应而变化；要求确定业务顺序的机制使用串行阶段，或由自身阶段显式收集决定后按业务规则结算。Runtime 不自动重排已经执行的行动。墙钟等待由模型连接管理，模拟时间由调度推进。

### 3.2 权威状态与完成发布

权威状态使用 SQLite 表、短事务和规范写入连接。插件在初始化时注册自己的表和索引，共享连接可以原子修改多个机制。冷正文与热投影拆表，减少数据库页、变化捕获和 Python 工作集合。查询连接只读并及时释放事务。正文可以使用压缩块或封存文件，向量索引作为可重建派生资源，小型临时工作集保持 dict。公开信息的文件路径与物理存储布局分别设计。

SQLite Session 的原生 changeset 保存完整步恢复增量。小字段输出的 changeset 可以很小，捕获过程仍会保存被更新行的原始列值；因此巨大正文同余额一行会放大内存，结构拆分是组件设计要求。外键使用数据库的约束与原生 changeset 应用语义。进程故障、重复恢复、删除、跨事务回滚、模式冻结和混合产物引用分别验收，具体协议见 [存储合同](storage-contract.md)。

初始数据库根与完整步增量形成恢复输入。每个完整 step 发布恢复身份，无需等待另外的十步检查点周期。当前数据库可以包含运行中已提交的进展，恢复链以完整步发布记录为准。分叉生成可写的新数据库及配置身份，其初次复制和历史应用成本单独测量。跨介质正文引用必须在完整发布前可达，文件通过业务事务内的 include_artifact 登记，Runtime 显式收集的引用在 complete 时合并。根压实、保留策略与可达清理需有实际消费者及独立恢复验收。

### 3.3 Thread、认知与产物

Thread 的元数据、追加事件和压缩正文块进入同一权威数据库。物理模型请求保存完整消息水位及请求参数，响应保存提供方原文。默认请求水位固定大小，重建请求按该水位取得完整消息；不得在每轮保存一次不断增长的消息序号数组。读取某段正文通过固定原始块定位，tail 以有限正文和可续读引用控制响应开销。

同主体、同 moment、同认知阶段的续激活通过持久 Thread 索引定位。内存 cursor 可加速当前进程，恢复后的身份由权威记录决定。提供方 session、工作区、已封存输出及行动回执使用可恢复引用；新 shell 会话需要消费旧输出时，通过该 Thread 的产物关联索引取得原文，避免重扫历史或重新执行行动。

自动召回、自动提取写入、主动记忆行动分别配置。记忆正文、所属主体、时间、重要性、状态和向量来源属于权威事实；检索结构由这些事实重建。提取结果、向量写入和成功回执的失败窗口通过持久 pending 状态及幂等消费验收。同一批的不同主体保留独立正文、向量和归属。访谈默认执行测量，incomplete 激活不得生成成功经验。

### 3.4 失败与并发

默认阶段顺序执行，显式声明互不冲突的阶段可以并发等待 Driver。完整阶段准备结果可由多个主体共用；SQLite 读事务必须在模型等待前释放。领域规则需要确定顺序时，研究者选择串行阶段，或显式采用先收集决定、后按既定顺序结算的协议；independent 本身不保证跨主体写入顺序。

领域处理器在部分写入后异常、Thread 权威写入失败和未知发布结果均使当前步骤停止。无一致性破坏的 provider incomplete 可以由明确的调度合同选择收集并继续其他主体；结果中必须保留 incomplete、原因及实际动作，不能标为正常完成。默认策略仍终止该步。取消须等待已开始的调用和任务退出，之后才能关闭资源或恢复。

CPU 计算首先下推成熟原生组件。在线帧和 Session 流使用同步原生 zstd，冷正文采用 SQLite 主键索引下的独立 zstd 帧；应用不维护压缩工作池。可选 compute_plugin 提供单运行共享 ProcessPoolExecutor，显式设置 max_workers 和 max_pending。进程提交量有界，批次字节量、调用方准备数据和返回结果仍由机制控制；权威写入留在拥有者进程，结果按业务语义安装。纯 Python 进程计算须把编码、传输和进程组 RSS 一起测量。公共接口语言与更换计算实现分别决策，详见 [语言决策](language-decision.md)。

### 3.5 验收映射

引用、scope、权限与动态行动首先通过两个主体、两个机制的直接测试，覆盖过期引用、目录数量、执行前条件改变、同一目标多行动和关闭后访问。插件主机通过独立失败清理测试。存储原型通过独立进程故障与固定活动集合增长试验。Driver、Thread、Memory、Schedule 的实际消费者与测试锚点列在能力表；独立审查、真实服务和整体性能分别保存验收证据。

每组能力的实现责任、预定测试与阶段见 [实施验收映射](acceptance-map.md)。作者先建立失败用例，完成直接验证后由非作者审查；确定性能力、真实提供方兼容和大规模性能分别留证。任何接入如果需要重建全量 World、复制每主体共享材料或裁剪完整认知输入，都应返回对应接口重新设计后再推进。

## 四、外部观察

外部观察的消费者包括运行监控、主体会话阅读、研究者分析和工作台。服务接入使用已经存在的 SQLite 状态及组件读取合同；本节规定跨层语义，已实现的参数与调用示例见 [外部观察合同](observation-contract.md)，剩余验收以 TODO 为准。

### 4.1 当前进展与完整身份

status 返回运行身份、当前阶段、活动主体计数、live_revision、已确认 complete_step 与其来源。最新权威完整身份来自不可变步骤描述符，current 内的完成水位作为确认下界分别呈现。进程正在执行、provider 正在等待、阶段失败与完整步骤完成应在外部可区分。轻状态读取不枚举全体主体、不解析 Thread 正文、不追赶历史查询索引。

当前状态每次通过短只读事务获得。普通信息分页按 2.2 的数据及权限依赖水位检查；要求整个运行处于同一版本的调用可以显式传 expected_revision。相关版本变化使游标失效，调用者可重新读取。需要稳定历史版本的分析请求显式准备一个选定完整步骤的查询视图，准备在后台执行，状态接口保持可读。初版一个服务同时维护一个准备任务和一个已准备视图，新准备成功后替换旧视图，取消与清理释放真实文件和连接。准备的 root 复制、链应用、磁盘峰值及取消延迟均属于成本报告。

### 4.2 持续读取

完整页游标与追加游标采用不同合同。Thread tail 按 thread_id 和已读取序号继续，即使上次已经读到末尾，也能在同一身份内读取后来追加的消息。消息原文采用分块引用，单个巨消息的首段、剩余长度和继续位置必须明确。Thread 目录也需可发现新增 Thread，避免观察者预先知道所有主体和会话。

一次响应同时说明读取内容属于 live 进展还是完整步骤所覆盖的前缀。当前数据库中的未完成事实可以用于诊断，恢复入口始终选用完整身份。服务不为每个慢消费者保存无限队列；消费者持有游标并拉取，等待通知可以优化延迟，通知不充当事实存储。观察进程重启后，客户端凭运行身份与持久序号继续读取。

### 4.3 公共读取与范围

Python、CLI 和 HTTP 使用同一份读取结果及错误分类。研究者以明确的研究访问身份读取，主体入口使用其绑定 scope；插件的信息提供者继续负责领域范围和数据投影。外部只读服务无需安装驱动、创建模型连接或执行插件初始化。插件若需要自定义研究视图，显式提供只读组装函数。

服务限制的是单次传输和在途资源，全部相关记录仍有精确总数和继续读取路径。巨正文走范围读取；数据表的字段、过滤、排序和抽样下推现有提供者。最终编码后的响应字节数属于预算，不能以 SQL 行数替代。慢请求、慢响应、断连及请求取消在独立工作槽中处理，释放槽位后仍可服务状态查询。

### 4.4 验收

独立进程模拟生产者卡在模型等待、正在提交短事务、正在完成步骤及异常退出。观察者需读到准确的当前水位、Thread 新增片段和最终完成身份。另用固定活动量扩大历史、单巨消息、持续更新导致页过期、后台准备取消和慢 HTTP 客户端检查时间与磁盘成本。最后由工作台消费这些真实输出，确认领域事实、主体会话和统计数字来源一致。

这一接口允许外部在完整步骤之间看到实际进展，并将恢复身份、当前数据与诊断状态分别标明。实时性的验收使用实际可见延迟和资源占用，不以轮询间隔或服务启动成功作为完成证据。

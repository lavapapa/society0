# Society0 Core 与插件系统 PRD

本文规定 Core 与插件系统的产品目标、职责边界和验收要求。现行能力与合同入口见 [实施结果](implementation-result.md)，旧版有效能力见 [能力对照](capability-parity.md)，采用方式见 [技术选型](technology-decisions.md)。实施、真实服务与发行状态由 [验收清单](TODO.md) 管理；各轮测量保留其报告中的源码身份与适用范围。

## 一、目标

Society0 支持研究者将多种机制组合成一个共享环境，使不同驱动的主体在环境授予的信息与行动范围内形成意图，再由机制决定其对世界的影响。环境状态、主体数量、历史材料和行动空间能够扩展，运行成本主要由实际工作集合决定。

### 1.1 使用与完成

机制作者用 Python 声明自己的状态表、信息视图、行动模板和阶段函数，依赖其他机制公开的服务。研究者选择插件、主体驱动与时间计划，完成初始化、运行、实时观察、历史分析、恢复和分叉。主体可以由规则、LLM 或其他决策模型驱动，使用同一套信息与行动语义。

研究者可从一个简单机制开始，逐步叠加通信、关系网络、记忆和资源机制。插件各自管理状态和规则，Core 提供组合与一致运行边界。产业、市场、税务等专属规则由外部环境仓库实现。全部有效能力按能力 ID 验收；旧接口和旧存储格式允许破坏兼容，废弃的 SimEngine、旧 socket 推送和过时执行器退出产品。

### 1.2 原则与性能

主体身份、完整认知材料、行动自主性、逐笔事实顺序、完整 Thread 和记忆属于约束。性能优化不得通过静默裁剪、强制结束、减少有用行动或降低原预算达成。实际限制导致的结束明确记录为未完成或失败。

固定活动集合扩大历史时，热步骤不全表扫描、不整 World 序列化；休眠主体不拥有常驻解释器和完整上下文副本；小字段更新不复制巨大正文；慢观察者不令运行端积累无界队列。全量分析、完整模型输入和巨文件整体修改的实际数据量成本直接计入报告。

### 1.3 复用边界

Core 维护社会模拟共同合同，成熟组件负责数据库、模型协议、压缩、shell 和通用并发。接入优先采用公开、可独立调用的 API。大型框架的相关功能可作为行为参考；源码复制将增加本项目维护责任，须核对许可、来源和实际删除收益。

语言采用 Python 公共接口与研究插件，成熟 C/Rust 组件承担相应热路径，TypeScript 保留在工作台。底层存储作为固定平台设施，不设置任意数据库可替换协议。插件扩展聚焦模拟能力。

## 二、合同

共同概念围绕一次主体参与展开：调度器建立时点，机制提供信息与行动，驱动提出意图，机制执行并产生反馈，运行时收束本步骤。所有插件共享这一过程，并使用稳定身份相互引用。

### 2.1 身份与信息

`Ref(namespace, kind, key)` 标识主体、对象或资源，解析时按需读取。`Moment(time, phase)` 表达模拟时点，revision 表达其内部变化。网络等待不推进模拟时间，多次写入可以属于同一时点。

Information 提供发现、文档范围读取和集合查询。信息可以是公开事实、他人声明、预测或传闻，保留来源、版本和关联对象；权威事实不会自动成为全体主体可见的信息。实际读过的材料和主观相信的内容由认知插件分别记录。

Access 绑定主体与时点，分别检查 discover、read、invoke，目录条目和数量也经过可见范围过滤。常见角色、归属和参与关系复用公共索引，复杂条件由机制函数表达；集合过滤在查询侧执行。访问范围、数据版本及继续读取游标共同约束稳定读取。

list/query 返回 items、total、next_cursor、revision；read 返回原文字节、总长度和继续位置。请求明确选择当前版本或固定版本，跨页版本变化可识别。精确总数、抽样、筛选和排序的成本必须声明；任何分页都保留取得全部相关内容的路径。

### 2.2 行动与驱动

Actions 注册按对象类型复用的模板，以 find、describe、invoke 三个稳定入口提供给主体。查询时绑定目标，执行时再次判断条件。模板不按主体数乘对象数预展开。大量模板的文字检索使用数据库现成全文索引，资格由机制查询和执行入口判断。

ActionResult 区分 accepted、completed、rejected 与执行故障。长过程受理后由未来阶段推进。业务拒绝允许继续决定；处理器部分写入后异常或取消，使当前步骤失效。成功回执与调用身份持久关联，同一有效运行内的传输重试不重放已成功动作。

`Driver.run(session)` 返回 completed、waiting 或 incomplete。规则驱动使用结构化服务；LLM 驱动将同一服务呈现为元工具和文件工作区。模型 SDK 接管单次请求协议，驱动插件管理行动预算、自然结束、研究者显式 required 约束、错误反馈和 Thread 生命周期。

模型 profile 显式声明提供方、认证方式和支持的参数。订阅端点和普通 API 的能力差异在运行前处理；不支持的温度、输出上限或工具格式不能静默删除。能力不足的 profile 无法承担对应研究合同。

### 2.3 认知与记忆

主体保存身份、persona 和主观状态，临时工作集合按激活创建。认知插件组合环境说明、precision、提醒和可选记忆。同一 Moment 重激活沿用 Thread 与信息会话，游标呈现新增内容，此前材料继续存在于完整历史。

Thread 追加保存请求、响应、工具回执和运行消息。请求按消息水位引用历史。LLM 激活入口解码一次完整 typed 历史，后续模型调用借用同一列表；活动主体在服务排队与工具等待期间保留该历史，激活结束后释放。独立记忆提取请求在共享许可授予后物化其完整输入。opaque 字段与签名经过保存、恢复和再次发送仍须有效。截断、流中断和额度耗尽是未完成状态。SDK 正常返回或出现完整工具参数都不足以证明成功，驱动消费完响应并确认该 profile 的明确成功终态后再执行行动。

Memory 分别配置自动召回、提取写入和主动工具三个开关。正文、原始向量与作业为权威数据，检索索引可重建。跨主体 embedding 合批保持每段原文与来源一一对应。准备、向量写入和回执分开验收；完整点之后发生的外部调用可能重算，不承诺任意外部服务恰好一次。

### 2.4 时间与完成

首版内置 FixedStep 与 PhasedSchedule，分别表达固定步骤和显式阶段计划。阶段函数完成选择、激活和机制结算；独立阶段可并发，同主体串行，信号可合并，只有活动主体创建任务。

局部业务变化通过短同步 SQL 事务完成，事务内不等待网络。跨机制同时生效的变化放在同一事务；允许延后的影响由后续阶段推进。共享状态的业务顺序由机制明确规定，计算工作者不争抢规范写者。

步骤收束全部必要行动、记忆作业和工件后发布完整身份。当前可查询状态、Thread 与可恢复完整点分别标识。失败步骤留诊断，恢复从可信完整点建立新运行。

## 三、架构

体系分为固定平台、语义 Core、内置插件与研究者机制组合。代码规模核算覆盖全部自有层，以下定义各层责任。

### 3.1 固定平台与 Core

固定平台提供 SQLite/APSW 存储、压缩正文、只读查询、资源许可和产物生命周期。数据库拥有事务、索引和行变更捕获；薄适配负责完整步身份、工件引用及恢复目录。公开实际需要的写事务、短读视图、追加正文和范围读取。

语义 Core 包含引用与时点、主体作用域、信息与行动路由、插件主机和步骤状态机。主机采用标准依赖图与上下文管理器，任务树采用 TaskGroup。Core 定义最小 Driver/Schedule 合同，不导入模型、向量库、shell 或社交机制。

依赖方向为“成熟组件 → 固定平台 → Core → 内置能力及领域机制 → 运行组合”。平台接受通用标识和字节，不反向导入具体机制；插件通过声明的服务依赖协作。外部观察使用只读服务，世界修改仍经过领域行动。

### 3.2 内置插件

基础主体层提供 Actor、Thread、认知输入、结果记录、FixedStep 与 PhasedSchedule。规则运行加载这一层及所选机制，无需模型、向量或 shell。配置中的驱动工厂按活动主体构建实例。

模型与认知层包括提供方适配、LLMDriver、embedding、Memory、Workspace 和 Shell。通用模型节点与工具分派采用 Pydantic AI Agent；领域行动资格、回执、完整 Thread 和步骤完成条件由语义 Core 保持。LLMDriver 使用 Actor 数据、Thread、Information、Actions 与模型提供方；Memory 按配置依赖提取模型及 embedding；Workspace 的服务安装只依赖平台存储，文件归属在数据层引用 Actor schema；Shell 依赖 Workspace 与 Information。compose 先汇集 schema 并建立初始数据，再安装服务。Actor 的驱动工厂因此可以依赖 Workspace，数据外键不被机械翻译为反向服务依赖。

机制层保留 Plain、RoundRobin、Social 的有效能力。通信、关系网络、曝光与推荐归机制；共享模型与向量资源按运行复用。安装依赖和业务阶段顺序分别声明。研究者可以组合多个机制实例，各实例有自己的命名空间。

### 3.3 作者接口

作者提交 `Plugin(name, requires, schema, initialize, install)`，复杂准备通过 prepare 生命周期完成。schema 采用普通 SQL，initialize 建立初值，install 注册信息提供者、行动及公开服务。资源使用上下文管理器，恢复时跳过初值生成。

典型机制只需状态表、信息提供者、行动函数和可选阶段函数。机制在规范事务中维护事实与索引，模型、压缩、文件、HTTP 和 OAuth 由公共设施承担。系统不要求每个机制拥有独立数据库、事件总线、进程和另一套配置语言。

运行前完成组合与初始化。运行中装卸、分布式共享可写 World 和通用离散事件引擎不进入首版。插件可替换驱动、调度和业务服务；底层存储与完整点协议由 Society0 统一维护。

### 3.4 文件式呈现

共享材料挂载到 /world，主体材料位于 /workspace，经绑定身份的视图取得。Bashkit 提供命令与管道，自有窄桥连接信息视图和私有增量层。世界变化通过 Actions，私有文件写入不授予业务修改资格。

大资料采用目录化投影：manifest 描述原文大小、版本、分片顺序与完整读取方法，parts 下是有界文件。分片改变读取组织，全部原文仍可取得。集合采用分层目录和有版本的数据页文件，按请求生成，避免预建整个文件树或巨型单层目录。

Bashkit 当前单文件读取会整文件物化，首版因此选择有界投影。私有巨文件整读与 copy-up 仍按完整文件计量。文本分片保证编码及边界可重组，字节材料保留精确范围通路；完整 cat 的输出内存仍随选定内容增长。分片大小控制每次读取成本，不构成主体信息或完整输出的删减上限。

热状态、Thread 元数据和小消息保持同库事务。Thread 大正文采用 SQL 索引下独立 zstd 小块；不可变批量正文采用 SQLite 工件与 ordinal/chunk 主键下的独立 zstd 帧。两种容器共用正文引用和读取合同，各自满足事务追加与批量封存。

## 四、运行

数据所有权、工作集合与提交边界共同决定性能和可恢复性。组件选型由 [技术选型](technology-decisions.md) 固定；以下规定其在仿真中的使用方式。

### 4.1 存储与观察

短 SQL 事务产生 live revision，SQLite Session 捕获变化，完整步骤封存变化与工件引用。当前数据按事务版本查询，完整步骤发布不依赖隔多步重写巨大根。恢复由根加完整增量重建新目录；长链可在离线维护时形成新根，保留需要的历史点。

工件先准备并耐久化，再登记引用，最后发布完整身份。失败窗口分别验证。复用已验证发布协议，缩减重复实现，不再造 WAL、压缩格式或行级撤销日志。长读导致的 WAL 保留、根复制和大行捕获分别计量。

在线 SQLite/WAL 使用本地文件系统；网络挂载用于封存与传输，跨机器观察使用 HTTP。同一文件系统的不可变工件可硬链接复用，跨文件系统复制并计入磁盘和耗时。

Python、CLI、HTTP 共享只读服务。status 返回活动步骤、live revision 与 complete step；固定完整点保持版本；Thread tail 用持久序号续读。首版实时访问采用按需轮询，时效由发布频率、轮询间隔与查询成本共同决定。完整事实读取不依赖客户端持续在线。

### 4.2 资源与计算

LLM 和 embedding 使用共享异步许可。容量由配置及端点能力决定，限流、重试和连接池各有明确所有者。SDK 隐式重试、自动模型切换与收费 fallback 默认关闭。物理调用和逻辑来源分别留证。

随机正文和 Thread 小块使用串行原生 zstd，移除自有压缩 future 队列。大顺序流的原生 workers 受统一预算控制；纯 Python 独立重计算用标准进程池，传紧凑批次或只读引用，按约定顺序安装结果。进程启动、IPC、原生缓冲及全部 worker RSS 纳入验收。

运行任务及资源收尾归明确拥有的任务树，排空后释放资源。调用方取消、重复取消和清理自身失败均验收。TaskGroup 对子任务取消的特殊处理不代替步骤失效登记，行动边界继续执行完整点规则。

### 4.3 订阅认证

首版订阅支持 Codex/ChatGPT 计划，与普通 API key 使用不同 profile。外部请求返回完整 Responses 结果，无需向使用者提供流式输出；端点要求的流式传输由适配层消费，并保留明确终态检查。正式第三方授权采用 OpenAI 公布的 Sign in with ChatGPT 计划接入及 Responses 合同；SDK 内置 Codex OAuth 的技术支持与该官方路径分别核验。实际模型资格和共享额度通过账户授权及未来真实请求确认。

认证设施使用成熟 OAuth/OIDC 组件管理授权、保存与刷新，仿真取得请求所需的短期凭据。凭据不进入插件状态、工件或模型上下文，主体数量不对应独立账户和登录。订阅额度耗尽时等待或结束，记录明确原因，无收费回退。

端点支持的请求参数在运行前核对；完整历史、客户端行动执行和流终态判断为共同合同。embedding 使用单独确认的服务或本地模型，不推断由 ChatGPT 订阅覆盖。其他 coding plan 根据提供方正式支持范围启用，协议兼容与订阅资格分别验收。

## 五、规模

规模估算按现行模块和目标责任逐项相加，覆盖 Core、适配、内置插件和外部接口。具体计数、区间与限制见 [规模与覆盖](size-and-coverage.md)。

### 5.1 代码预算

语义 Core 目标约 1,200–1,800 物理行。全部 Python/Rust 库预计约 8,000–10,500 物理行，包含平台适配、认证、内置插件及公开接口；已有前端、示例和测试另列，全部属于维护范围。这是设计预算，实施后按同一脚本重新计数。

减少量主要来自旧提供方管理、重复任务清理、HTTP 协议层和自有压缩定位。完整 Thread、行动回执、记忆与恢复语义仍需应用代码。不能通过压缩排版、移出统计目录或删除能力达到预算。

### 5.2 资源边界

启动成本取决于插件与实际加载索引，活动内存取决于同时激活的主体、完整模型输入、原生缓存和工作批次。历史落盘，普通热页按索引读取；全量分析和恢复的扫描成本单列。

必须保留的实测边界包括 Session 大行、完整上下文、Chroma 活跃向量、seek table、私有巨文件修改和长恢复链。库替换不能使这些物理成本消失，验收分别扩大主体、历史、单对象和并发。

## 六、验收

产品按失败用例、消费者测试和独立审查验收。隔离库试验、组合产品、真实服务与主体效果分别记录，执行状态见 [验收清单](TODO.md)。

### 6.1 覆盖要求

能力矩阵全部有效 ID 均有责任模块和验收位置。每项能力至少覆盖正常路径与关键负例，重设接口保留行为对照。订阅认证、正文格式与文件投影另设新增规格。可选依赖同时验证启用和未安装路径，纯规则运行保持轻量。

确定性对照比较逐笔事实、顺序、完整上下文、原始向量和恢复状态。模型 SDK、压缩器、shell 与 HTTP 均通过真实公开接口验证。源码覆盖和分支覆盖按被测源码采集，实际测量见 [覆盖报告](../../research/core-next/acceptance-20261004/capability-review.md)。

### 6.2 故障与组合

数据写入、正文准备、完整发布、记忆回执和外部响应间逐窗口中断，以独立进程重开。覆盖部分行动失败、连续取消、安装失败、清理失败和客户端断开。Hypothesis 状态机生成组合，独立审查发现形成固定回归。

贯穿场景覆盖双机制共享对象、规则与 LLM 混合、同 Moment 重激活、发现后行动失效、工作区恢复、记忆三个开关、长 Thread、历史分叉及真实产物工作台。对比主体看到的材料和最终行动，保留逐笔顺序。

### 6.3 性能与效果

相同大根或有依据的同量级数据分别固定活动扩大历史、固定历史扩大活动、扩大单正文和并发。报告环境计算、模型等待、编码压缩、持久化、观察、恢复、总磁盘及进程组峰值内存，比较连续多步增长斜率。

用索引访问、读取和物化字节说明复杂度，以重复耗时和内存支持选型。目录化资料与动态行动必须完成真实信息获取和行动效果对照，工具更少、文本更短不作为单独成功标准。

### 6.4 交付条件

实施按固定平台与语义 Core、主体认知与内置机制、公共入口组织。每阶段更新对应规格，以失败用例和实际消费者验证修改，并经独立审查。最后源码的确定性全量、原生平台组合、真实端点短程及实际大负载各自留证，测试端点依本次明确的账户和费用授权选择。

新版完成的依据是能力完整、故障边界正确、资源成本有证据且外部使用顺畅。具体执行和交付范围由 [验收清单](TODO.md) 维护；选型证据、账户资格、真实模型行为与完整业务长期表现分别对应其报告中的消费者和运行合同。

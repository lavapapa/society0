# 设计文档：统一状态与持久化架构

**版本**: 1.0
**状态**: 最终方案

## 1. 演进与背景：从 `StatePatch` 到统一架构

### 1.1 最初的挑战

我们最初的设计面临一系列关于状态管理的根本性挑战：

*   **`StatePatch` 的困境**: 要求 `Skill` 和 `Behavior` 手动创建并返回 `StatePatch` 列表，这使得函数实现变得繁琐、不直观，且容易出错。
*   **上下文的丢失**: `StatePatch` 只描述了“结果”（状态变成了什么），但完全丢失了“原因”（是什么行为、在哪一步、哪个节点导致了这个变化）。这使得日志分析和行为追溯变得极其困难。
*   **`WorldState` 的冗余**: 存在一个凌驾于 `Environment` 之上的 `WorldState` 概念，使得“世界”的边界模糊不清，增加了不必要的复杂性。
*   **原子性缺失**: 多个 `StatePatch` 的应用不是原子性的，中途失败会导致状态不一致。

### 1.2 核心思想的演进

经过多轮深入讨论，我们否定了 `StatePatch`、`ActionIntent` 等“补丁式”方案，最终确立了一套全新的、统一的设计哲学，其核心是：

**任何状态变更，都必须在一个“上下文栈”中进行，并由框架自动拦截、记录和应用。**

这个思想将引导我们构建一个统一的、能够同时解决状态管理、日志、持久化、恢复和分支所有问题的优雅架构。

## 2. 最终设计方案：基于“上下文栈”与“Node级事务”

### 2.1 核心原则

1.  **`Environment` 即世界**: 我们**废除 `WorldState` 类**。`SimEngine` 只持有一个顶层的 `environment` 对象，它包含了 `agents`, `globals` 等所有世界状态。架构变得扁平、清晰。
2.  **自动事件生成**: 我们**废除 `StatePatch` 的返回机制**。状态变更的日志（`Event`）将由框架根据当前的“上下文栈”**自动生成**，开发者无需关心日志记录的任何细节。
3.  **`Node` 级事务边界**: 状态变更的原子性边界被定义在**单个 `Node` 的执行过程**中，这为细粒度的恢复提供了可能。

### 2.2 关键组件与工作流

#### a. 上下文栈 (`Context Stack`)

*   **定义**: 一个存在于 `StepFlow` 实例上的、支持“写时复制”的不可变栈结构。它负责在执行流程的每一层，记录下当前的上下文信息。
*   **工作流**: `StepFlow` 在执行 `Node` 时，会通过一系列的 `with` 语句，将 `step`、`node`、`operator`、`action`/`behavior` 的信息逐层推入一个临时的 `context_stack` 拷贝中。
*   **并发安全**: 由于每个并行的执行路径都操作自己的 `stack` 拷贝，因此该设计是并发安全的。

#### b. 状态代理 (`StateProxy`)

*   **定义**: 一个临时的代理对象，它被创建并传递给需要修改状态的 `Action` 和 `Behavior` 函数。
*   **工作流**:
    1.  开发者在 `Action`/`Behavior` 函数内部，可以像操作普通对象一样，极其自然地编写代码，例如 `env_proxy.state["posts"].append(new_post)`。
    2.  `StateProxy` 会**拦截**这个操作，但**并不会**立即提交。
    3.  它会在内部将这个修改意图（目标路径、操作、值）**暂存**起来。

#### c. `Node` 级事务

*   **定义**: 每个 `Node` 的执行过程，都被包裹在一个“事务”中。
*   **工作流**:
    1.  在 `StepFlow` 执行一个 `Node` **之前**，开启一个事务，并创建一个空的“待提交事件列表”。
    2.  在 `Node` 执行期间，所有通过 `StateProxy` 发起的修改，都会被拦截，并连同当前的 `context_stack` 一起，被转换成一个富语义的 `Event`，然后追加到“待提交事件列表”中。
    3.  在 `Node` **成功执行完毕后**，框架会“提交”事务：将“待提交事件列表”中的所有 `Event` **一次性、原子性地**写入 `events.jsonl` 日志文件。
    4.  **然后**，框架再将这些变更**应用**到内存中真实的 `Agent` 和 `Environment` 对象上。
*   **原子性**: 这确保了只有成功完成的 `Node` 才会产生任何持久化的日志和状态变更。

### 2.3 富语义事件 (`Event`)

*   **定义**: 我们只有一个通用的 `StateChangeEvent` 类型，其语义完全由其 `context_stack` 提供。
*   **结构示例**:
    ```json
    {
        "event_type": "STATE_CHANGE",
        "change": { "target": "agent_alice", "path": "state.money", "op": "add", "value": 10 },
        "context_stack": [
            {"type": "step", "id": 10},
            {"type": "node", "id": "work_node"},
            {"type": "behavior", "name": "process_work_results", "params": { ... }}
        ]
    }
    ```
*   **日志**: 我们的 `events.jsonl` 就是由这样一个个富语义事件组成的、只增不减的日志流。

## 3. 对五大核心过程的支撑

这个统一的架构完美地支撑了您提出的所有核心需求。

### a. 状态管理 (State Management)

*   `Action`/`Behavior` 的开发者体验变得极其自然，只需通过代理对象修改状态即可，无需关心事件生成和日志记录。
*   实现了“分散式（在各自函数中）提出修改请求，集中式（在事务提交时）统一处理”的优雅模式。

### b. 日志系统 (Logging System)

*   `events.jsonl` 成为了我们唯一的、结构化的、富语义的真理之源。它自动捕获了每一次状态变更的完整“前因后果”，具有极高的可分析性和可追溯性。

### c. 持久化 (Persistence)

*   **核心持久物**: `events.jsonl` 事件日志流。
*   **缓存/快照**: 定期保存的、包含所有世界状态（`agents.state`, `agents.properties`, `agents.reminders`, `env.state` 等）的完整快照。
*   **自定义类型**: 对于 `networkx.Graph` 或向量数据库等复杂类型，其所在的 `Environment` 或 `Memory` 模块需要实现自己的 `snapshot()` 和 `load_from_snapshot()` 方法。`PersistenceManager` 在创建快照时，会调用这些方法来获取可序列化的数据（例如，图的边列表），并在恢复时调用相应方法来重建对象。Milvus Lite 的物理文件可以被视为快照的一部分，进行整体备份和恢复。

### d. 初始化与恢复 (Initialization & Resume)

*   **全新初始化**: 
    1.  `SimEngine` 加载配置。
    2.  `SimEngine` 创建 `Agent` 和 `Environment` 的内存实例。
    3.  `SimEngine` 调用 `env.initialize()`，这个过程会产生第一批“创世事件”并被记录。
    4.  `SimEngine` 保存“第 0 步”的初始快照。
    5.  开始运行 `Schedule`。
*   **恢复 (`resume`)**: 
    1.  **恢复到 `step N`**: 加载 `step N-1` 的快照，然后从 `events.jsonl` 中重放 `step N` 的所有 `Event`。
    2.  **恢复到 `step N` 的 `node M` (高级功能)**: 加载 `step N-1` 的快照，然后重放 `step N` 中，所有在 `node M` **之前**执行的 `node` 所产生的 `Event`。框架应提供此高级接口，并告知用户可能存在的“非稳态”风险。

### e. 多分支 (Multi-Branch)

*   **实现**: `Event` 数据结构中的 `metadata.branch_id` 字段是关键。
*   **创建分支**: 从 `main` 分支的 `step N` 创建 `dev` 分支，意味着从此刻起，所有新生成的 `Event` 都将被标记为 `branch_id: "dev"`。
*   **切换/恢复分支**: 只需在重放 `Event` 日志时，根据 `branch_id` 进行筛选即可。

## 附录：设计决策与演进之路

一份好的架构文档不仅应阐述最终的设计，更应记录其演进的轨迹和关键的决策过程。本章节旨在回顾我们在设计统一状态架构时所经历的核心争议、您的关键洞察，以及我们最终达成共识的思考路径。

### A.1 核心争议一：状态变更的范式 (从 `StatePatch` 到自动事件)

*   **最初方案 (v1)**: `Skill` 和 `Behavior` 函数需要手动构建并返回一个 `StatePatch` 对象列表来描述状态变更。这是一种“指令式”的模式。
*   **遇到的问题**: 您敏锐地指出，这种模式对于 `Skill` 的开发者来说是**不自然的、繁琐的**。一个自然的 `publish_post` 函数，其心智模型应该是直接操作列表，而不是去构建一个复杂的数据结构来“描述”这个操作。
*   **您的关键洞察**: 您提出，状态变更的“上下文”应该被自动捕获，而不是手动写入。这引导我们走向了“自动事件生成”的核心思想。
*   **最终方案 (v2)**: 我们引入了“上下文栈”和“状态代理 (`StateProxy`)”的设计。开发者现在可以编写符合直觉的代码，而框架则在后台自动拦截这些操作，并结合完整的上下文栈，生成富有语义的、可追溯的 `Event`。这解决了 v1 方案的所有弊端。

### A.2 核心争议二：世界模型的层级 (`WorldState` vs. `Environment`)

*   **最初方案 (v1)**: 框架中存在一个顶层的 `WorldState` 类，它包含了 `Environment` 和 `Agents`。这是一种“容器式”的架构。
*   **遇到的问题**: 您对这个设计提出了质疑，认为它导致了“世界”概念的模糊和架构的冗余。Agent 应该直接活在 `Environment` 中。
*   **您的关键洞察**: 您提出了**“`Environment` 即世界”**的核心观点，主张采用更扁平、更清晰的架构。
*   **最终方案 (v2)**: 我们采纳了您的建议，**废除了 `WorldState` 类**。现在，`SimEngine` 直接持有一个 `environment` 对象，该对象内部包含 `agents` 和其他所有世界状态。这使得整个架构的层级更少，概念更清晰，职责更明确。

### A.3 核心争议三：能力与法则的定义 (`tool`/`rule` vs. `Skill`/`Behavior`)

*   **最初方案 (v1)**: 我们曾探讨过多种方案，包括“意图-规则分离”范式，但都未能完美解决“直接行动”和“受规则约束的行动”之间的关系，导致概念重叠和实现上的僵硬。
*   **遇到的问题**: 您用 `dog.bark()` 这个生动的比喻，一针见血地指出 Agent 的能力应该是直接且有效的，而不是所有动作都要通过一个间接的“意图”层。
*   **您的关键洞察**: 您主张必须为这两类不同的“动作”找到更贴切的命名和更清晰的职责划分，并提出了 `Behavior` 和 `Skill` 的初步构想。
*   **最终方案 (v2)**: 基于您的洞察，我们最终确立了“能力-法则”合作范式：
    *   **`Behavior` (行为)**: 由调度器自动触发的“世界法则”或“条件反射”。
    *   **`Skill` (技能)**: 由 Agent 主动调用的“能力”。它可以直接产生效果（返回 `StatePatch`），也可以在需要时，在其内部调用一个或多个 `Behavior` 作为逻辑库来辅助计算。
    *   这完美地解决了两种行为模式的共存与合作问题。

### A.4 核心争议四：事务的边界与状态生效时机

*   **最初方案 (v1)**: 我曾提议将事务边界设在 `Step` 级别，并在 `with` 块结束时才“延迟提交”状态变更。
*   **遇到的问题**: 您立刻指出了该方案的两个致命缺陷：1) 在嵌套调用中，由于状态未立即生效，会导致严重的上下文不一致问题。2) `Step` 级别的事务边界粒度太粗，无法支持您期望的 `Node` 级恢复。
*   **您的关键洞察**: 您明确指出，**事务边界必须在 `Node` 级别**，并且状态的修改必须能**立即在内存中生效**，以保证后续逻辑的正确性。
*   **最终方案 (v2)**: 我们采纳了您的设计。`StateProxy` 的修改会**立即应用**到内存中的真实对象上，但产生的 `Event` 会被暂存。只有在整个 `Node` 成功执行完毕后，这些 `Event` 才会被**原子性地写入**持久化日志。这既保证了嵌套调用时的状态一致性，又通过 `Node` 级的日志提交，为细粒度恢复提供了坚实的基础。

# 连续步骤的旧版与当前版对照

本试验补充 T12 的分阶段验收，回答固定活动规模时累计历史是否拖慢步骤，以及新的分页存储格式带来什么代价。基线为 7e98f11，当前版为本工作树。两版从同一逻辑完整 World 起点初始化，再由各自原生格式编码根检查点；起点业务内容相等，文件字节与存储格式不同。

## 一、条件

每次运行固定 20 个活动条目，历史分别为 5,000 和 50,000 条，连续执行 20 步。每步修改全部活动条目的余额并追加 20 条不可变事实。纯环境和含 Agent 模式各运行旧、新两个独立子进程，共八个进程。所有运行顺序执行，使用同一 Python 与依赖环境。

Agent 模式执行真实 execute_action_loop 和 ActionSet 工具，每步由确定性 provider 先调用一次 adjust，再自然结束。全部 prior_messages 持续提供，Thread 保留完整消息；DummyMemory 读回并提供全部记忆正文。provider 与记忆计时包含本地复制和处理，不包含真实网络、嵌入或 Chroma。Agent 总耗时包含 provider、DummyMemory、动作循环、工具及 Thread 读写，因此不得将子阶段与总阶段重复相加。

每次根发布后恢复并比较初始状态，末步后恢复并逐项比较最终状态；跨版本进一步严格比较初始、最终、恢复状态、81 条 Thread 消息、20 条记忆全文及 40 次 provider 的完整消息输入。四组对照全部相等。正确性比较、最终恢复及每步工件目录计量均在步骤计时之外；根恢复发生在步骤前，会影响后续峰值 RSS 的高水位口径。

## 三、判断

固定活动条目和增量记录数下，历史从 5,000 增至 50,000 条没有导致当前版环境或持久化耗时按历史规模增长。Agent 耗时随完整会话与记忆增长符合本试验持续传入全部正文的条件，两版均保留这一工作量。

当前 SQLite 分页格式的根发布时间及小增量持久化均高于旧 gzip 格式，每步检查点约 38 KB，旧版约 2.6 KB。该结果明确暴露分页、独立记录定位及数据库页结构的固定成本，不能据此宣称整体提速。较大起点的当前版峰值 RSS 更低；是否值得采用要结合独立读取、分页延迟和索引规模验收共同判断。

原始逐步数据见 stage-comparison.json，复现脚本为 benchmarks/runtime_stage_comparison.py。脚本通过 git archive 读取旧提交，在 TemporaryDirectory 中生成旧源码和全部大工件；八个子进程正常结束后临时目录已自动删除，仓库只保留小型脚本、指标 JSON 和本说明。此结果覆盖合成 World、确定性动作循环与本地记忆替身，真实模型和 Chroma 的延迟及长期增长继续由相应端到端验收负责。

# 性能验收综合判断

本报告按 TODO 的 V04 条件归并已有原始测量，并为 X09 的独立取舍提供证据入口。验收对象是新版 Core 的存储、读取与确定性运行机制；产业环境尚需把领域热字段、业务索引和工作集接入这些机制。本轮采用 Chroma 的现有检索合同，sqlite-vec 保留为隔离候选实验。全量原文、主体信息、动作预算与恢复边界均未因性能测量而缩减。

## 一、依据

各阶段分别保留冻结源码、实际执行脚本、环境和原始指标。真实根来自 R3/8pct/attempt-003，旧整体 gzip 为 173829194 B，原状态约 1.879 GB；按声明展开为 1448471 条记录后，记录 JSON 合计 1894775315 B。旧解析峰值约 9.91 GB，原 World 常驻约 5.37 GB。两种表示的包装不同，逐值和顺序核对承担等价证明，压缩字节比承担空间比较。

### 1.1 源码身份

真实全根冷批次的 storage、_json_chunks、datasets 及执行探针与 `0ef012a` 逐字一致，原始身份记录为 [cold-full-source-comparison](cold-full-source-comparison-20261004.json)。32 核服务器 X08 使用 `b51c5f9` 的独立归档源码，11 个直接产品文件比较与实际执行脚本均保留在 [x08-source-comparison](x08-source-comparison-20261004.json) 和对应 executed 文件。源码采用直接字节比较。

本次首次盘点 HEAD 为 `9180498`，检查过程中其他 owner 正常提交到 `6b6417f`。时间点记录见 [本轮源码核对](performance-acceptance-source-20261004.json)。在该时间点，storage、_json_chunks、datasets、threads、memory 与 `0ef012a`、`b51c5f9` 均相同；models、llm、results、resource_managers 与 `b51c5f9` 相同。information_sql 的授权目录发现、interaction 的授权分发及 Action 故障传播、runtime 的故障收束已有修改。大根读取探针直接使用 StageReader/Datasets，因此其直接执行路径保持；规则和模型步骤经过 Actions/Runtime，历史计时仍归原冻结版本。后续 models/llm 会话传输修订发生在第二次核对期间，其差异单列于[收尾身份记录](performance-acceptance-source-final-20261004.json)，最终 SDK 路径需要自己的直接组合与真实验收，旧 X08 时间不代替这项验收。

### 1.2 测量口径

正常运行 current/WAL 位于服务器本地 `/tmp` overlay，原始来源在 Ceph；未在共享网络文件系统上部署 WAL 写入器。服务器为 32 个逻辑 CPU、Python 3.12.9，本地为 macOS ARM64、12 个逻辑 CPU、Python 3.12.12。所谓冷读为独立新进程，操作系统页缓存保留。磁盘分别报告逻辑长度与 inode 去重物理分配；单次结果、阶段 RSS 和进程高水位各按原始定义引用。Python 显式 fsync 计数与 SQLite 原生同步分开，未测部分不推定为零。

## 二、状态

V04 的真实大根、单大 entry、恢复和查询条件已有直接证据。核心改善来自热投影与不可变正文分离、原生流编码和按需读取，巨记录的业务拆分仍由领域机制完成。

### 2.1 全根与空间

最初同源 SQL 正文内嵌 fixture 的单 current 为 708517888 B，含 root 的目录为 1417036675 B。dbstat 显示压缩 payload 占单库约 82%，1121607 条记录不超过 1 KiB；逐记录压缩和两份正文成为主要空间来源。经过有限窗口、完整 SQLite 索引及随机读取对照，正式实现采用每批一个不可变 SQLite 工件、64 KiB zstd 共享块；同文件系统恢复以硬链接共享工件，跨文件系统明确复制。

最终全部 1448471 条记录及顺序逐值相等，源运行全部文件 226538252 B，相对早期内嵌 fixture 减少 84.0%，约为原 gzip 的 1.30 倍，较上一版可定位组件约 332.94 MB 减少约 32%。源、恢复和只读视图三目录 inode 去重分配为 226689024 B。正文只有一个批次工件，文件数随批次增加；当前可变 SQL、Thread 与 Memory 同库历史仍会在可写恢复时复制，硬链接收益适用于已封存工件。相关原始数据见 [全根冷批次](cold-datasets-native-full-20261004.json)，阶段推导见 [冷批次报告](cold-datasets-performance-20261004.md)。

完整导入为 59.494 s：源解压/逐条 JSON 解码 29.294 s、原生 JSON 编码 19.989 s、zstd 3.159 s、SQL 与控制 7.040 s、Python 显式同步 0.0122 s；计时外逐值验证 74.672 s，总 CPU 134.088 s。峰值 335253504 B 包含最大单条解析。原先旧根一次性转换读取需要保留旧基线源码，实际运行进程加载新版 kernel；全根验证从转换 SQL 流式读取，未再次构造旧 World。

### 2.2 单值与局部更新

最大声明记录约 29.948 MB。初期同源 fixture 对其整值修改的 20 步中位编辑为 7.410 s、进程峰值 297.90 MB；拆出的一个热字段中位编辑 0.188 ms、峰值 21.32 MB。该整值耗时使用早期 Python 编码，后来 RapidJSON 对同一最大记录的单独编码测量为 0.108 s；这两个不同范围的计时不能直接计算整步加速比。

10 MiB 异质正文的小对照明确了分块边界风险：尾部修改、前置等长修改、前置长度增长的 changeset 分别为 267 B、101175 B、16175495 B，Session 原值捕获均约 10.49 MB。原生 changeset 解析证实最后一组包含 162 条 UPDATE 的旧/新压缩 BLOB；热字段变长移动后继边界。存储分块改善范围定位和缓冲，业务侧巨记录整值重写仍有实质成本。证据见 [边界原值](large-root-alignment-20261004.json) 与 [原生解析](large-root-alignment-native-20261004.json)。

成熟流编码保留任意大整数、Unicode 原文与顺序，同时可能为输入字符串建立完整 UTF8 缓存。实际 8 MB Python Unicode 对象增加约 7 MB UTF8 缓存，生命周期跟随原字符串。64 KiB 输出与 512 KiB 压缩待处理队列均不是总进程内存上限，输入、固定前缀、输出、原生压缩器及 SQLite Session 另计。

### 2.3 读取与恢复

独立进程打开全根 1.31 ms，固定第一页 1000 次请求 219.28 ms，巨记录跨块 64 B 为 0.287 ms。后续真实继续分页另测 1000 页，读取 42172 条、完整响应累计 64.43 MB、墙钟 2.374 s；1000 个随机目标共 3000 次范围调用 0.495 s，原文字节重合核对全通过，两负载峰值 22.84 MB。详见 [访问原始结果](dataset-access-real-20261004.json)。单次读取作用域缓存最后一个块，1000 条同块小记录的实际消费者只打开一次文件、读取一次 BLOB、解压一次。

初始全根可写恢复 4.59 ms、只读准备 3.63 ms；再进行 20 步 header 更新后恢复 11.66 ms，原状态及范围字节相等。后者每步 Session 内存恒为 2416 B，中位写入约 0.16 ms、发布约 0.73 ms，整个冷进程峰值 21.94 MB。该成本得益于本地同文件系统工件硬链接与小 SQL 根，跨文件系统复制、实际业务索引重建以及累计同库 Thread/Memory 的恢复成本需另预算。链长增加时原生 changeset 应用具有累计工作量，现有证据没有承诺恢复与历史无关。

## 三、增长

固定活动量扩大历史与固定初始历史扩大活动是两种不同问题。本轮分别使用索引计数、实际步骤与容量实验，避免用一次读取的小 RSS 推断完整认知运行的上界。

### 3.1 固定活动量

早期 1k/10k/100k SQL 原型在活动 64 条时，查询 VM 157、阶段 VM 178、增量 152 B；它支持原生索引方案，现行产品证据另列。最新短复验通过 Thread、Memory、Social 与 usage 的 13 项相关测试，命令及输出见 [历史工作量复验](performance-acceptance-history-20261004.txt)。Thread 历史 1000→10000 时 append/tail VM 为 599/81→599/81；Social 历史 100→10000、固定活动池时为 483→483；资源调用历史 100→10000 的当前累计查询为 396→396。Memory 当前召回在 10→10000 历史版本下 SQL 工作量保持测试的 1.15 倍范围；该例使用替身向量客户端，证明范围为 SQL 当前投影路径。

实际工作区实验在 1000 主体、1 个活动 shell、8 MiB 未改文件下，10 次激活均无新增工件或正文读取。目录 100→10000→50000 时枚举时间与返回元数据按目录规模增加，峰值增量约 3.0→7.9→27.5 MB；完整目录枚举自身的增长属于实际返回量成本，不能描述为固定页查询。见 [工作区规模](workspace-product-scale.json)。

### 3.2 固定初始历史、扩大活动

为补充活动规模维度，本次以 `9180498` 独立归档源码复用固定执行探针，在三个新进程分别运行 1、8、32 个规则主体和 20 步；初始事件历史均为零，每个主体每步做一次相同加一，完整恢复全部余额为 20。结果及可复跑脚本见 [活动量原始结果](performance-active-scale-20261004.json)、[探针](performance-active-scale-probe-20261004.py)。

每步中位墙钟分别为 4.43、4.00、6.61 ms，事务数为 12、19、43，进程峰值为 40.04、36.86、37.67 MB，目录为 0.581、0.674、0.943 MB。前五步与后五步平均耗时为 3.41→4.66、4.34→3.62、7.77→6.59 ms。每档仅一次短运行，小负载固定开销和系统抖动明显，事务计数随实际动作增加比绝对时间更有解释力。该试验覆盖规则路径的活动规模，LLM/Memory 的递增活动量和高并发驻留仍未形成同等矩阵。

### 3.3 完整认知与向量容量

32 核服务器以固定 8 主体、20 步分别测规则、确定性 SDK 的完整 LLMDriver、再加正式 Memory 提取及真实 Chroma。每步中位数为 5.83、72.56、185.14 ms，进程峰值为 36.05、95.45、161.10 MB，目录为 0.67、2.97、8.80 MB；后两组分别 160、320 次模型调用，记忆组产生 160 条原文与向量，恢复逐值相同。Memory 钩子与模型/SQL 计时嵌套，无法相加。规则和 LLM 组末五步未呈增长，Memory 组前五步 175.79 ms→末五步 210.01 ms，记忆钩子 91.62→128.48 ms，瞬时 RSS 150.08→158.67 MB；早期召回条数尚少，后期达到 top_k，候选索引同时增加。结果见 [步骤原始数据](step-cost-server-20261004.json)。

真实 Chroma 1.5.9 的独立 1k/10k×1024 维测量，查询后 RSS 126.48→172.33 MB，磁盘 9.30→46.39 MB。当前默认 Rust 后端没有将旧 Python Settings 的 1 MiB LRU 字节配置传给原生缓存；指定后仍约 173.33 MB。运行级 collection 覆盖全部当前有效记忆，历史查询还需要临时索引。SQL 历史投影有界不等同于向量索引有界，完整 Memory 运行不得引用领域冷读 22 MB 作为总预算。详见 [Chroma 证据](chroma-residency-20261004.json)。

本 release 保持该已明确的 Chroma 合同。sqlite-vec 的 1k/10k 对照属于独立可选路线：普通表按 actor 过滤原生 exact 距离可降低这组驻留，但 float32 派生、近似/精确候选差异、单主体大集合线性工作量及部署成熟度尚需后续验证，不改变本轮 Memory 产品。

## 四、计算

多核收益按工作类型归属，核心规范写入继续保持既定顺序。CPU、内存、通信和事件循环响应共同决定取舍。

### 4.1 多核与通信

X08 在 32 核服务器执行 32 个约 1 MiB 完整输入任务，四工作者、最多八个待处理任务，进程路线包含 spawn、输入 pickle、输出 IPC。原生 JSON 加 zlib 的串行/线程/进程墙钟为 1.035/0.308/0.391 s，CPU 为 1.126/1.086/1.512 s，采样进程组 RSS 为 31.41/42.35/151.03 MB；每份压缩输出均在父进程全值验证。纯 Python 数值核对应 0.497/0.504/0.259 s，CPU 0.515/0.516/1.095 s，RSS 24.83/24.78/137.39 MB。

原生字节计算采用线程具有明确收益，纯 Python 重计算可用进程交换墙钟与额外 CPU/内存。RSS 为约 20 ms 采样最高值且共享页重复计入，CPU 包含退出子进程的启动/导入/通信；计时内父验证与后台计算重叠。数据见 [并行原始结果](parallel-server-20261004.json)，专项非作者审查见 [X08 review](x08-spec-review-20261004.md)。

### 4.2 同步与响应

本机旧编码阶段的实际 Thread 4×10 MiB 产品线程路径中位 296 ms，相比同步 912 ms 缩短约 67.5%，事件循环最大空窗仍约 207 ms。事务外暂存改善响应并增加临时 I/O，未成为默认产品。后来原生 JSON 已替换 Python 遍历，上述绝对空窗属于当时产品快照。随后当前编码路径的 4×10 MiB 实际 Thread 补测，作者与独立复跑的事件循环最大间隔分别为 108.88 和 71.10 ms；独立 observer 的 status+tail 最大响应分别为 1.278 和 1.078 ms，四份完整原文逐值相等。两轮小样本和高水位口径见[最终实时性](final-realtime-20261004.md)与[独立复验](final-realtime-ci-storage-review-20261004.md)，尚未形成长期响应分布。

SQLite WAL FULL 的本机 180 次短事务测得 183 次原生同步，NORMAL 为 3 次；产品仍保留 FULL。同一只读连接复用在 1000 张表、100 次小查询时从 82.56 ms 降至 1.386 ms，连接数由 100 降为 1；嵌套读另建临时快照，结束请求释放游标。长读者阻止 WAL 回收的原型已有证据，最终并发 observer/长读者下的 WAL 高水位和尾延迟尚未形成服务器负载曲线。原始边界见 [持久化报告](persistence-performance-20261004.md)。

## 五、结论

V04 各项已经有可定位证据：真实大根及完整值、巨 entry、固定活动历史索引、规则活动量增长、独立恢复、顺序/随机页、完整 LLM/Memory 步骤、32 核线程/进程均已测量。结果支持当前存储与计算路线：原文保留、小工作集运行、不可变正文共享、原生增量和成熟原生编码。测试及实测同时揭示了适用边界，验收应以这些具体能力为单位。

仍未覆盖的规模组合包括：真实产业机制迁移后的资金/库存/业务索引和同完整点前后对照；长期高有效记忆量及历史召回临时 Chroma 索引的总驻留；递增 LLM/Memory 活动并发与 Shell 的联合步骤；物理冷缓存、服务器长期多读者 WAL 峰值、跨文件系统大根复制与 Ceph 封存尾延迟。changeset 链恢复和同库认知历史复制的工作量随保留历史增加，领域冷热拆分也需要实际机制采用。已有 20 步短试验不证明无限期稳定性。

因此本轮可关闭相应机制选型与已测消费者的性能判断，V04 的广义整系统规模保证须保留上述范围。X09 的验收权归独立审查者，本报告不以作者综合说明代替非作者结论。新权限、故障传播与模型传输修订继续用当前提交的直接测试和实际部署验证；性能数字始终绑定它们真正执行的源码身份。

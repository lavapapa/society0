# 大根存储试验

本试验以同一旧根的完整原始状态检验新版存储成本，区分一次性转换、正常进程的工作集、局部增量和独立恢复。它使用基础 SQL fixture，保留原声明记录的顺序、路径类型、操作和正文，尚未提供产业业务查询索引或 Environment 迁移。

## 一、方法

转换来源是 R3/8pct/attempt-003 的初始完整根，旧 gzip 为 173829194 字节，解压 JSON 约 1.879 GB。转换读取工具使用产品快照 `537ac50` 中的旧 `source_state`、`PersistenceSchema` 与 `_v4_root_entries`。这些仅用于基线转换与逐值对照；测量进程加载新版 kernel，不构造 World。旧接口最终移除后，复跑转换需要保留该独立基线部署，不构成新版兼容 API。

每条声明记录完整编码到 64 KiB 原始块并压缩，SQL 表以 sequence/chunk 定位。小头表记录正文大小，独立热字段表保存试验修改值。初始化时记录固定活动样本，后续读进程通过主键访问，避免为选择样本扫描全表。原路径保留在记录正文；本 fixture 未验收按业务路径查找的能力。

整值修改组读取巨记录、修改值并重新编码；拆分组修改独立热字段，冷正文保持原文。检查点均使用实际 StageStore Session 与完整描述符。记录变化前 Session memory、完成前文件空间、完成后空间、关闭后空间；盘占同时报告逻辑长度和 st_blocks，包含 current、root、WAL、changesets、artifacts。新旧值全等校验位于计时之外。远端 current 运行在本地 `/tmp` overlay，源 gzip 位于 Ceph，原运行只读。

## 二、分块边界

2026-10-04 本机独立小试验使用固定随机字节编码成 10 MiB 异质正文，热字段初值 9。尾部更新为 10，编辑 92.96 ms、含 complete 的 CPU 262.39 ms，changeset 267 B；前置等长更新为 8，编辑 95.96 ms、CPU 264.57 ms，changeset 101175 B；前置增长为 10，编辑 88.87 ms、CPU 261.39 ms，changeset 16175495 B。三组 Session 捕获均为 10492848 B。单次测量，未声称统计稳定性。

另一次原生 changeset 流解析确认：尾部变化产生两条 UPDATE，旧/新 BLOB 共 74/75 B；前置等长产生一条 UPDATE，旧/新 BLOB 各 50561 B；前置增长产生 162 条 UPDATE，旧/新 BLOB 共 8085125/8085132 B。约 16.18 MB 输出来自原生 UPDATE 同时携带新旧压缩块。逐记录编码能够限制额外缓冲并提供范围定位，热字段长度变化依然会移动后续块的边界。冷热字段拆分避免这项重新编码和原值捕获成本。

原始数据分别在 `large-root-alignment-20261004.json` 与 `large-root-alignment-native-20261004.json`。最初对高度重复正文断言整值 changeset 必然超过拆分十倍失败：原生 Session 合并相同主键下完全相同的块，尾部小修改的输出仅 163 B。该失败保留在 `large-root-fixture-green-r3-20261004.txt`（文件名源于当时预期）；后续断言改为原值、捕获内存和原生实际增量的可检验合同。

## 三、复跑

小型验收命令为 `PYTHONPATH=src .venv/bin/python -m pytest -q tests/experiments/test_core_next_large_root_probe.py`。`core_next_large_root_probe.py` 提供 convert、verify、read、whole、split、restore 六种独立进程模式。真实 source 使用冻结旧根；run/target 必须是本任务新目录。whole/split 修改当前 fixture，各路线应从同一初始完整点恢复到独立目录，以免混入上一组修改。恢复另起进程测峰值，转换进程解析旧 JSON 的历史高水位不作为新运行内存。

运行探针的读取称为冷进程读取，操作系统文件页缓存未清空。完整检查点历史可以持续增长，热读与修改的计数和耗时须另做固定活动量的连续步骤对照。当前小试验已经逐值验证类型、顺序、跨块范围读取、未完成写入排除以及整值和拆分两条恢复路径；真实大根结果见下一节。


## 四、真实大根

单次转换输出 1448471 条原声明记录，JSON 总长 1894775315 B。解析旧根并准备声明耗时 36.49 s，新建 SQL 根耗时 538.21 s，总 CPU 575.55 s。转换进程峰值 9.905 GB 来自旧 JSON 解析。初始化的编码与插入成本显著，当前结果未将其视为已解决。

冷进程读取 1000 次固定主键用时 16.80 ms，读取最大记录中间的 64 B 用时 0.253 ms，进程峰值 21.15 MB。最大声明记录为 29948413 B。整值修改它的 20 步中位编辑时间 7.410 s、完整发布 3.523 ms，进程峰值 297.90 MB；独立热字段组中位编辑时间 0.188 ms、完整发布 0.822 ms，峰值 21.32 MB。两组 Session 捕获分别约 3.85 MB 与 2608 B，20 步 changesets 共 636283 B 与 920 B。此处热字段是基础 fixture 的测试字段，未证明任何产业查询或业务拆表已经迁移。

完整 20 步恢复耗时 1.847 s，独立进程峰值 25.23 MB。初始完整点 fork 约 1.90 s。恢复后的独立验证进程按原顺序逐条比较全部 1448471 条声明记录，全部相等；比较含解析原 JSON 共 95.54 s。验证进程约 9.91 GB 的峰值与恢复进程分别记录，不混为运行内存。

单个 current.sqlite 为 708517888 B，初始 root.sqlite 同样大。关闭后的完整目录为 1417036675 B，物理分配为 1417052160 B。相对原 gzip 173829194 B、上一版可定位组件约 332.94 MB，磁盘成本仍很大；恢复和 fork 的新目录继续复制 current 与 root 两份。原 gzip 的整体格式与新库的当前权威、索引、独立恢复边界不同，比较同时说明能力和复制范围，不能凭低内存单独批准空间结果。

只读 dbstat 统计显示压缩 payload 合计 580678154 B，占单库 81.96%；chunks 表 656211968 B、chunk 索引 21692416 B、record 头表 17485824 B、热字段表 13090816 B。1121607 条记录不超过 1 KiB，233866 条不超过 256 B，376 条至少 64 KiB。后续有限样本比较将区分逐记录压缩、跨记录重复以及 current/root 重复正文的成本，保持来源位置和逐值对照，不重新转换全根。

## 五、空间取舍

代表样本使用现有转换库，记录全部原 sequence，未重复转换根。最终连续窗口实验在全根分散选取八个窗口、每窗口最多 512 条记录，排除超过 64 KiB 的单条值并单列其位置；训练集合明确排除全部窗口位置。窗口原文合计 4344970 B，每一种结果均逐值解压核对。最终证据为 `large-root-codec-windows-64k-20261004.json`；早期 `large-root-codec-windows-20261004.json` 有少量训练重叠，保留为过程记录，最终判断采用严格分离版本。

逐记录 zlib level 3 为 1802664 B，压缩 86.18 ms；32 KiB 字典的逐记录 zstd level 3 为 1113621 B，压缩 18.59 ms，体积减少 38.2%。字典训练本身耗时 34.15 ms，字典需持久保存并在读取时驻留。逐记录格式保持单条读取粒度：八个窗口共 800 次确定位置读取实际解压 868515 B，zlib 用时 6.36 ms，字典 zstd 用时 1.80 ms。这里是小样本单次压缩实验，未计 SQL 元数据、文件定位、冷盘读取和压缩器原生工作内存，也未将收益外推到全根。

64 KiB 原文目标的 zstd 分组为 547980 B，压缩 8.14 ms；1 MiB 分组为 476539 B，压缩 8.72 ms。对应 800 次随机读取分别解压 49647209 B 与 336754812 B，用时 19.10 ms 与 147.83 ms，分别约为所需单条原文的 57.2 倍与 387.7 倍。64 KiB 分组比 1 MiB 多约 15% 压缩体积，随机解压量减少约 6.8 倍。测试每次实际解开目标组，未用驻留组缓存隐去放大；缓存可以改善有局部性的访问，其额外常驻和命中率需要独立验收。同尺寸分组 zlib 分别为 604630 B 与 573064 B，说明跨记录重复本身占据相当份额。

分散位置的小样本另比较路径拆出：整条逐记录 zlib 为 177901 B，将路径单独分组压缩、剩余正文逐条压缩合计 156911 B，减少约 11.8%。这只衡量原文表示的压缩，不含为路径新增 SQL 索引的成本。最大记录首、中、尾三个现有块原文合计 195069 B，zlib 为 27913 B，zstd 为 22556 B；大型异质记录与小记录的结果分别保留，未用其中一组代表全根。

现成文件系统硬链接在本地 APFS 与服务器 `/tmp` overlay 均通过 64 MiB 不可变文件试验。目标与来源共享同一 inode，目录持久化后链接分别约 0.276 ms 与 0.182 ms；删除来源后目标逐字节等于生成原文。两个路径的 st_blocks 求和会显示 128 MiB，按设备与 inode 去重后的实际共享分配为 64 MiB。证据在 `artifact-link-local-20261004.json` 与 `artifact-link-remote-20261004.json`。可变 SQLite current 不适用这一共享方式；跨文件系统的独立复制成本仍需另测。

## 六、下一步

当前证据支持先减掉 current 与 root 的重复冷正文。可做最小候选：热字段与不可变正文引用留在权威 current，冷正文使用少量封存的只读 SQLite 文件，每个文件保存现成主键索引和压缩 BLOB，作为 StageStore 已有不可变 artifact 发布。同文件系统恢复可硬链接已封存文件，跨文件系统显式复制。这样继续使用 SQLite 的定位、标准压缩库与已有完整点恢复机制，避免逐小记录建文件；正文文件数量应由封存批次决定。尚未实现此候选，也尚未验收封存失败、同一冷片段引用复用、完整点所需片段集合及 source 删除后的恢复。

首轮候选可先保逐记录与现有大值分块，只对小记录评估持久字典，减少新增分组定位机制。64 KiB 分组作为后续空间对照保留，只有包含实际 SQL 索引、随机读取、封存和恢复后的总成本测量支持时再采用。当前分散记录字典收益及硬链接证据足以说明优化方向，尚不足以预测全根最终目录体积。只读完整点准备另可复用同一个恢复物化过程，省去可写 fork 才需要的新 root；该改动已有 Observation 消费者，应保恢复引擎单一。

结论是，新 kernel 已展示按需读取和小工作集恢复，巨大热 entry 的整值重编码仍需领域冷热拆分，空间复制仍需进一步处理。后续验收同时比较完整目录占盘、随机读取放大、正常步骤工作集与 fork 独立性，逐值恢复始终作为同一条成功条件。

复现部署说明：实际运行脚本 `large-root-runtime-command-20261004.sh` 中的 `benchmarks/core_next_large_root_probe_runtime.py` 是当前提交 `benchmarks/core_next_large_root_probe.py` 的原文副本，仅改部署文件名。已从远端取回该实际文件，保存为 `large-root-executed-runtime-20261004.py`，逐字符比较一致。`benchmarks/core_next_v04_diag.py` 的实际源保存为 `large-root-diagnostic-command-20261004.py`。复跑时把这两个文件复制到运行脚本所列文件名，kernel 源使用冻结 `537ac50`，旧转换读取工具按第一节的独立基线部署定位。

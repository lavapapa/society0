# 真实流式用量与缓存核对

本次核对读取两次失败运行的完整 Thread、物理调用事实和短用量投影，并由主控执行一次独立流式重放。研究者未读取凭据或自行调用提供方。结果解释同时受原始字段与 SDK 聚合方式约束。

## 一、事实

`cache-runtime-evidence.json` 逐项记录 `chain-live-01` 与 `round-live-02` 各八次物理请求。每个物理 ID 对应一个响应事实，响应标准化缓存读字段、SQL 物理调用记录和聚合投影相等。两次运行各报 90,112 缓存读取 token；提供方命名字段 `prompt_cache_hit_tokens` 也为正。这排除了 SQL 投影重复计数，却没有证明 SDK 终态聚合值等于一次请求最终累计量。

旧端点探针为非流式：约 1,379 token 的短前缀和 8,099 token 的相同长前缀均报告零命中。真实工具循环随后出现正值，说明在实际运行中发生过命中。现有材料无法给出固定触发阈值、准确命中 token 总量或缓存带来的延迟收益。提供方缺失的缓存写入字段仍为未知，SDK 类型默认零与提供方明确报告零分开处理。

## 二、聚合

主控执行的 `stream-default-live-01/result.json` 来自 `round-live-02` 第一个真实请求的相同消息、工具和设置。探针通过原生 OpenAI SDK 收集每个 chunk 的 usage，不执行模型产生的行动。九个 chunk 携带累计 usage；末条为输入 1,574、输出 76 token，逐条相加为输入 14,166、输出 445 token。输入相加值恰与原失败运行首调用 SDK 终态 14,166 相同；重新生成的输出长度与原调用不同，故输出只在本次流内比较。

当前安装 Pydantic AI 的 `models/openai.py` 在 `_usage += chunk_usage` 默认路径相加。`openai_continuous_usage_stats=true` 改走 `_usage = chunk_usage`，并通过现成模型设置发送 `stream_options.continuous_usage_stats=true`。由此确认旧失败运行的输入、输出及缓存聚合数量受到累计 chunk 重复相加影响。90,112 不能作为费用或缓存节省量；原始事实保留，后续运行应采用经端点验证的累计配置。`stream-continuous-direct-02/result.json` 已确认端点接受该设置：九个累计 usage，末条输入 1,574、输出 77 token，耗时 39.41 秒。此探针证明参数接受性与流的累计语义；新产品运行的 SDK 终态替换行为再由 chain-live-03 核对。先前经代理的 ReadTimeout 独立保留，直连补验使用与产品一致的 trust_env=False。

## 三、规模

两次运行实际登记七个 meta 工具。第一请求四条消息的 JSON 共 504 字符，工具 JSON 共 4,552 字符，消息与设置整体共 5,206 字符。随着八轮完整消息增长，最后一请求分别为 14,854 和 15,510 字符。上述数值由已保存请求重新序列化计算，用于说明输入构成；它们既非网络字节数，也非模型 tokenizer 结果。

流式重放记录 `request_json_bytes=5894`，其中包括序列化空白与 Unicode 的 UTF-8 字节差异。所谓每调用约 17K 输入 token 的主要已证实问题来自 SDK 对累计统计相加；本次末条 1,574 提供了直接反例。历史八次请求没有保存原始 SSE usage 序列，无法逐次逆推出真实最终数量。探针中的 `sdk_chunk_json_bytes` 是 SDK 对象重新序列化大小，同样不当作网络传输计量。

新运行的使用量需要以适配后计量与原生流最终 usage 对照为依据。保留失败运行与原始统计有助于追溯，但其累计数额不再承担费用、规模或缓存收益判断。

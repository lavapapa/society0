# 完整步骤与多核边界

本次把小型完整步骤和独立计算任务分开测量。服务器使用已提交 `b51c5f9` 的 `git archive` 副本，正式运行依赖环境由真实验收组安装；相关产品文件逐字节核对见 `x08-source-comparison-20261004.json`。执行脚本的固定副本为 `x08-executed-core_next_step_cost.py` 与 `x08-executed-core_next_parallel_codec.py`，命令见 `x08-server-command-20261004.txt`。临时数据库在服务器本地盘，退出自动清理，没有调用外部模型服务。

## 一、步骤

三个独立进程均运行 8 个主体、20 个完整步骤，领域阶段按默认串行语义激活主体，对每个账户执行相同的加一行为。规则组通过 Runtime 和 Actions 调用规范 SQL；LLM 组使用正式 ModelProvider、LLMDriver、Thread、行动回执和 Results，仅 SDK 返回值由确定性响应替换；记忆组再接正式 memory_plugin，真实 ThreadMemoryExtractor 及 Chroma 1.5.9，提取和 embedding 使用固定响应。20 步后全部账户恰为 20，完整点恢复后逐项相等；记忆组另外核对恢复后的全部正文块、短元数据和原始向量字节，最终有 160 条有效记忆。Shell 未加入此工作负载。

规则组每步耗时中位数 5.83 毫秒，其中 phase 为 4.37 毫秒、完整点发布 1.36 毫秒，19 次短事务合计 3.50 毫秒；整个进程峰值 36.05 MB，运行目录 0.67 MB。LLM 组每步中位数 72.56 毫秒，phase 70.07 毫秒、发布 2.36 毫秒，99 次事务合计 38.24 毫秒；160 次物理模型调用，峰值 95.45 MB、目录 2.97 MB。SDK 固定响应构造每步仅约 0.46 毫秒，其余包含上下文读取、原文编码、协议解析、Thread 与行动记录。

记忆组每步中位数 185.14 毫秒，phase 181.85 毫秒、发布 3.16 毫秒，179 次事务合计 71.23 毫秒；包含提取在内共 320 次模型调用，峰值 161.10 MB，目录 8.80 MB。Memory before/after 钩子每步中位数 103.97 毫秒，模型请求范围 60.32 毫秒，领域加一约 0.92 毫秒。模型提取和 SQL 事务位于 Memory 钩子内部，因此这些细分计时有重叠，不能相加成另一总数。目录包含规范 current/root/changesets、Thread、Results 和 Chroma 文件，使用逻辑文件长度统计。

前三组前五步与末五步平均总时间分别为 7.01→5.20 毫秒、81.19→73.44 毫秒、175.79→210.01 毫秒。记忆钩子为 91.62→128.48 毫秒，进程瞬时 RSS 五步均值约 150.08→158.67 MB。前五步每主体只有 0–4 条可召回经验，后五步已达到默认 top_k=10 的输出量，同时候选索引继续增长；这 20 步不能证明记忆检索成本与历史无关。它暴露了实际完整认知组合中新增信息与索引的成本，并与单独 Chroma 容量实验相互补充。

原始服务器数据在 `step-cost-server-20261004.json`，本机三组合对照在 `step-cost-local-memory-20261004.json`。本机单进程总墙钟分别约 0.181、1.322、2.780 秒，服务器约 0.213、2.690、5.377 秒；总墙钟还包括初始化、每步 RSS 采样与最后恢复。服务器版本为 Python 3.12.9、32 个逻辑 CPU。本次没有改变 WAL FULL 设置，事务计时包含编码与 SQLite 提交，无法把全部差额归给 fsync。

## 二、并行

编码任务每次接收约 1 MiB 完整 Python 值，经正式原生 JSON writer 与 zlib 压缩后返回全部压缩块，父进程逐值解压验证。共 32 个任务，固定四个工作者；线程传递对象引用，进程采用 spawn 并实际序列化输入和输出。待处理任务最多为工作者数的两倍，没有预先构造全部任务副本。32 份输出总字节均为 19,821,067，逐值验证全部通过。

串行、四线程、四进程墙钟分别为 1.035、0.308、0.391 秒，采样到的进程组 RSS 最高值分别为 31.41、42.35、151.03 MB。总 CPU 为 1.126、1.086、1.512 秒。线程在这类释放 GIL 的原生压缩上更合适；进程减少墙钟却需要额外解释器、输入 pickle、输出 IPC 和较高的组内存。父进程的完整解码验证约 0.25–0.28 秒，包含在墙钟内，并与后台计算重叠，不能简单相减得到“纯压缩时间”。

纯 Python 数值任务接收相同大小量级的完整浮点列，逐列计算均值、方差、最小值和最大值，32 份结果与串行基准严格相等。串行、四线程、四进程墙钟为 0.497、0.504、0.259 秒，进程组 RSS 为 24.83、24.78、137.39 MB，总 CPU 为 0.515、0.516、1.095 秒。线程没有改善此 GIL 主导的负载；进程约缩短一半墙钟，同时总 CPU 约翻倍，进程组驻留增加约 113 MB。该例说明只有足够重、可独立提交的计算才值得支付进程通信与资源成本。

CPU 总数采用父进程 `process_time` 加已退出子进程 `RUSAGE_CHILDREN`，包含进程启动、导入、pickle 与测量用 ps 子进程；另存 worker 内核 CPU 用于区分。RSS 每约 20 毫秒枚举父进程及子孙，排除正在测量的 ps 本身，报告的是采样最高值而非严格瞬时峰值；GIL 与调度可能推迟采样。多进程 RSS 相加也包含共享页的重复计量。原始结果见 `parallel-server-20261004.json`。

## 三、判断

本轮支持保留原生编码与有界共享压缩线程池。其收益来自独立不可变字节的计算，规范 SQLite 写入仍由唯一 writer 按既定顺序执行。同步调用等待线程结果仍可能阻塞运行事件循环，外部只读观察者的响应与内部主体调度应分别测量；已有异步 spool 实验的额外 I/O 与所有权成本仍有效。

数值进程试验可以支持后续机制把已声明独立的批量计算提交给成熟进程执行器，但不支持把共享可变环境、每个插件或每个主体自动迁到单独进程。当前测量没有世界复制，也没有把多核内核加速外推为整步加速。真实提供方的等待、服务容量、失败与上下文边界由独立的 15 项真实套件验收。

结合全根冷数据与本轮完整认知步骤，领域冷读、Thread 证据、短事务和向量索引已有可区分的成本口径。后续判断应优先看具体运行的有效记忆规模、请求并发和纯计算占比，再选择额外资源；本轮没有以裁剪历史、压缩主体信息或降低既有行动预算换取数字改善。

# 当前存储的同步与压缩成本

本次实验定位新版单写入器的实际成本，使用独立临时数据库、合成正文和真实 Thread/StageStore 写入路径。数据用于选择下一步实现，覆盖本机 CPU 与本地文件系统；服务器本地盘及封存到 Ceph 的对照仍待执行。全部临时大文件在进程结束前删除，原始 JSON 与命令记录保存在本目录。

## 一、同步与查询

`core_next_persistence_probe.py` 通过 APSW 原生 VFS 的 `xSync` 委托计数，同时单独计 Python 文件同步。环境为 macOS 26.6.2、arm64、12 个逻辑 CPU、Python 3.12.12、SQLite 3.53.4。每种模式 30 轮，每轮包含输入、请求记录、物理响应、assistant 消息、tool receipt、工件准备和关联，共 180 次短事务。

FULL 的短事务累计墙钟为 34.61ms、CPU 31.79ms，183 次原生同步累计 6.51ms；NORMAL 为 27.59ms、CPU 25.27ms，3 次同步累计 2.29ms。工件准备及关联另有 150 次 Python fsync，完成发布另有 64 次；这揭示重复同步的成本，也表明本机同步延迟很低。实验中的 NORMAL 修改仅作用于独立探针，不改变产品默认值。每组完整发布后均从根及 changeset 链恢复，消息数量验证通过；断电持久性需要额外故障验收。

每次读取新建 SQLite 连接的固定成本随 schema 增长。100 次同一主键查询，在 20、200、1000 张表时分别为 7.53、21.40、83.23ms；实验性复用一条只读连接并在每次请求结束回滚短快照，对应 1.20、1.49、1.87ms。该结果支持进一步考虑由调用线程拥有的有界连接复用。它没有验证长读事务、跨线程共享连接或正式连接池。

## 二、实际压缩

`core_next_compression_probe.py` 对同一 base64 异质正文执行四次 Thread 消息写入。每个配置运行三次独立进程，以下为中位数。当前同步与同步线程路线均在规范 writer 内完成编码、压缩和 SQL 写入；冻结路线先同步将任意 Python 值流式编码到临时原文，再由后台线程压缩到临时块文件，最后规范 writer 按块写入。已有 bytes 路线假定调用方已经拥有完整不可变 JSON bytes，省去冻结原文文件，其预编码时间单独记录。

10MiB 正文的四次写入，同步墙钟 912.12ms、CPU 881.95ms；4 线程压缩墙钟 273.76ms、CPU 924.25ms，墙钟约提升 3.33 倍，CPU 增加约 4.8%。冻结路线墙钟 419.95ms、CPU 965.46ms，其中冻结 106.32ms、规范 writer 提交 100.51ms；已有 bytes 路线墙钟 312.57ms、CPU 877.12ms，writer 提交 100.68ms。冻结路线累计额外写 70.8MiB、读相同字节；已有 bytes 路线累计额外写、读各 30.8MiB。临时文件没有 fsync，其生命周期由同次写入控制，尚未进入完成权威。

1MiB 正文对应同步 88.31ms、4 线程 29.43ms、冻结 44.18ms、已有 bytes 29.56ms。128KiB 正文对应 11.77、8.29、12.07、9.82ms，线程收益开始受到调度成本限制。额外阈值实验显示 256KiB 正文同步 22.48ms、4 线程 10.20ms；512KiB 对应 44.75、16.41ms。候选实现可先缓冲至 256KiB 再决定使用线程，以有界前缀代替全量预扫描。

10MiB 的 2、4、8 线程墙钟分别为 456.77、273.76、221.67ms，CPU 分别为 918.88、924.25、958.07ms。4 线程在这台机器上取得大部分收益；8 线程进一步缩短约 19% 墙钟，使用更多并行计算资源。该选择尚需服务器 CPU 对照，不能直接推成跨机器最优值。

## 三、响应与内存

探针另外运行每 1ms 尝试一次的事件循环观察任务，每次实际执行 StageReader 短查询。10MiB 的同步、同步线程、冻结、已有 bytes 四条路线，最大调度间隔分别为 686.08、205.24、55.81、29.69ms。同步路线连续 writer 调用的调度顺序会使一个间隔覆盖多条消息；这些数值表示本实验的实际响应空窗。冻结与 bytes 路线的间隔 p95 分别约 1.83、1.72ms，但最大值仍受冻结与 SQL 提交影响。四条路线的观察查询次数中位数分别为 2、2、148、149。同步线程路线改善吞吐，同时仍占用调用它的事件循环。

计时阶段结束立即记录写入峰值，随后才做全文读取逐值验证。10MiB 的同步、同步线程、冻结、bytes 写入高水位分别约 77.0、81.1、81.3、91.4MiB；输入构造后的历史高水位分别约 74.0、73.7、73.7、86.0MiB。ru_maxrss 是进程历史高水位；两者差值可能低估阶段实际新增驻留，不能当作精确增量内存。bytes 路线的预编码构造曾同时拥有 Python 输入和编码结果，历史高水位保留了这段成本。

待处理原始块引用上限为 8×64KiB，即 512KiB。此外还有正在产生的一个原始块、已取出的返回块、完成 future 的压缩结果、每个 zlib 工作区和 SQLite/Session 自身内存。512KiB 不代表整个流水线内存上限。输入本身在整个记录期间驻留。原文冻结方案避免把可变 Python 容器跨 await 交给线程；模型内部新建且未公开的响应值有潜在独占路径，但现同步 trace hook 需要单独接口改造，本实验没有改动该调用链。

## 四、判断

本机数据支持先将大正文接入共享、有界的原生压缩线程池，保持规范 SQLite writer 独占。小正文保留短路径。事务外冻结具有更好的事件循环响应，同时增加临时 I/O、资源收尾和接口复杂度；应在服务器本地盘复测后决定是否进入产品。已经不可变的 bytes 可以采用更低成本的独立准备路径，普通可变值仍需要明确冻结或独占合同。

7 个探针测试覆盖跨 UTF8/转义原文全等、待处理原始字节预算、首次 await 前冻结、取消等待 worker 后清理文件及四条路线的真实 Thread/只读查询消费者。每次基准在计时之外完整读取全部消息并逐值比较；这组验收没有替代正式产品失败注入、进程崩溃或真实提供方组合验证。原始文件前缀为 `compression-pipeline-r*`、`compression-select-r*` 与 `persistence-cost-local-20261004.json`；最初未区分写入和验证峰值的探针结果单独保留为早期证据。

### 4.1 产品候选复测

采用显式 Writer.encode_chunks 后，三个消费者共用 StageStore 懒创建的 4-worker 池，每次消息复用该池。真实候选的三次独立进程中位数，128KiB、1MiB、10MiB 各四条消息分别为 12.20、31.56、296.03ms；10MiB 相对原同步 912.12ms 缩短约 67.5%，CPU 919.86ms 相对原同步增加约 4.3%，写入峰值约 80.9MiB。最大事件循环调度间隔仍为 207.45ms，符合同步等待的已知边界。原始文件为 `compression-product-r*`。

独立审查指出异步探针第二次取消可能提前释放正在被原生线程使用的文件。复现测试先失败，随后改为持续屏蔽取消等待 worker 结束再清理，7 个探针测试重新通过；该修正未进入产品异步接口。正式同步候选包含原文全等、两个消费者共享单池、短值不启动池、作用域失效、半消费收束、关闭线程退出、原始队列字节计数、压缩错误整体回滚且池可复用的作者验收，独立产品审查另行进行。
